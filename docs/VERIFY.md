| D-POLARS-GLOB | workaround (found 2026-11-07) | `pl.read_parquet(path)` and `pl.scan_parquet(path)` treat `[`, `*` and `?` in a path as a glob pattern even for a path that names one existing file. | D-POLARS-PANIC | workaround, residual risk (found 2026-11-07) | A damaged Parquet file can make `pl.read_parquet(path, glob=False)` raise `pyo3_runtime.PanicException` (`pl.exceptions.PanicException`), whose bases are `BaseException` and `object`: it is not an `Exception`, so `except Exception` and `except pl.exceptions.PolarsError` do not catch it. Workaround: `rinchen.synth.shards._read_parquet` catches `PolarsError`, `PanicException` and `OSError` and raises `DataError`, so a panic counts as an invalid shard that is regenerated. Parquet page checksums are not checked, so a flip that leaves the structure intact decodes to different data; the structural checks alone (ids, row count, types, nulls) caught only 0.3% of 1,500 flips of a 98,112-byte shard in the final review, while 63.7% decoded to different candidates with no error (27.5% on an 8-row, 3,248-byte shard). Every single-bit flip of the shard file, through `ShardStore.load`: all 9,888 flips of a 1,236-byte shard (941 caught by the digest, 4,136 unreadable, 249 structural, 4,561 left the rows unchanged), all 26,712 of a 3,339-byte shard (7,461 digest, 11,046 unreadable, 232 structural, 7,972 unchanged) and 3,000 random flips of a 98,203-byte shard (1,843 digest, 1,117 unreadable, 8 structural, 32 unchanged): none decoded to different rows without an error. Still open: an allocation abort cannot be caught (bit 0 of byte 63 of the 1,236-byte file and bit 0 of byte 66 of the 3,339-byte file abort the process with SIGABRT, return code -6; the committed sweep test works on the 1,236-byte shard and flips bit 1 of byte 63, never bit 0), and the digest is not a signature (whoever can rewrite a shard can rewrite its digest). The crash cases, a partial write or a truncation, were already caught. |

| D-POLARS-SIGINT | workaround in the D6 client and in `run_logged` (found 2026-11-08, final review) | Once `polars` is imported, a SIGINT sent to the process does not wake the main thread's blocking `concurrent.futures.wait()` (an untimed lock acquire): the Python handler runs only when the call returns by itself. Through the real binary (`rinchen train ablate`, the tiny ablation of the D7 gate, no `--timeout`, SIGINT sent to the `rinchen` process 4.0 s into `eole train`): before the fix exit 130 came 25.91 s after the signal (26.8 s in the first measurement by the Task 8 implementer; with `--timeout 600` the same signal was handled after 0.47 s, because a timed wait is interrupted); after it, exit 130 came 0.19 s and 0.17 s after the signal in two runs, with no `eole` process left. Workaround: `run_logged` waits through `_wait_for_exit`, in slices of 0.2 s (`_INTERRUPT_POLL_S`) that never run past a monotonic deadline, so the `timeout` semantics, the kill of the process group and the messages are unchanged; `test_a_real_sigint_interrupts_the_wait_while_the_child_runs` sends a real SIGINT to a child that lives 6 s and fails by assertion with the bare wait (5.61 s after the signal, where the fix raises within 0.01 s, 15 runs under 26 busy loops). Not fixed outside D6 and `run_logged`: every `rinchen` command whose main thread blocks without a timeout (a lock, a join, `Queue.get()`, an untimed `Future.result()`) is affected the same way, so Ctrl-C is not delivered until the call returns; the other D4 and D5 commands were not examined.
