## D6 findings

Upstream behaviour found while building the synthetic-data stage (`docs/runbooks/06_synthetic.md`).
All four are guarded in this repository, not fixed upstream. Environment of every reproduction:
polars 2.1.0, ctranslate2 4.8.4, CPython 3.14.10, Linux, 2026-11-07 (`D-POLARS-SIGINT`: 2026-11-08).

| Check ID | Result | Notes |
|---|---|---|
| D-POLARS-GLOB | workaround (found 2026-11-07) | `pl.read_parquet(path)` and `pl.scan_parquet(path)` treat `[`, `*` and `?` in a path as a glob pattern even for a path that names one existing file. A file `run[1]/shard-00000.parquet` raises `ComputeError: failed to retrieve first file schema (parquet): expanded paths were empty` (both functions), and the same call with `glob=False` reads its 2 rows. A file named `a*.parquet` beside `ab.parquet` and `a1.parquet` returned the ids of all three files (`['a', 'b', 'a1', 'ab']`) and, with `glob=False`, only its own (`['a', 'b']`). In the shard store this made every existing shard unreadable after a shard directory containing `[` was created, and a resume silently regenerated everything (found in review). Workaround: `glob=False` on every Parquet read in `rinchen.synth.shards`, `rinchen.corpus.readers` and the read-back of `rinchen.corpus.writers.write_corpus`, each with a test. The read-back was missed at first: `rinchen synth run --out-dir 'out[1]'` generated every shard and then failed with the `ComputeError` above (exit 1, a traceback, and the earlier manifest already removed); found in the final review, fixed 2026-11-08 (a `[1]` and a `[a-z]` out dir through the CLI and `write_corpus` with `[` in the directory or the name now complete; the real binary against a loopback server wrote `corpus.parquet`, `counts.json` and `manifest.json` for `out[1]`, `out*`, `out?` and `out[a-z]`). `pl.read_parquet_metadata` has no `glob` argument and reads the file named (checked with `out[1]` beside `out1`). |
| D-POLARS-PANIC | workaround, residual risk (found 2026-11-07) | A damaged Parquet file can make `pl.read_parquet(path, glob=False)` raise `pyo3_runtime.PanicException` (`pl.exceptions.PanicException`), whose bases are `BaseException` and `object`: it is not an `Exception`, so `except Exception` and `except pl.exceptions.PolarsError` do not catch it. Single-bit flips of a 3,324-byte shard-shaped file (8 rows of 2 candidates), 150,000 trials, one bit at a time with a parent process restarting the child after an abort: 38,581 `PolarsError`, 45,528 decoded to the same frame, 65,607 decoded without error to a different frame, 276 `PanicException` and 8 aborts of the whole process (`memory allocation of 2305843009213693952 bytes failed`, return code -6). On a 156,403-byte shard (512 rows of 4 candidates, 3,000 flips): 1,101 errors, 22 unchanged, 1,877 different, no panic, no abort. Workaround: `rinchen.synth.shards._read_parquet` catches `PolarsError`, `PanicException` and `OSError` and raises `DataError`, so a panic counts as an invalid shard that is regenerated. Parquet page checksums are not checked, so a flip that leaves the structure intact decodes to different data; the structural checks alone (ids, row count, types, nulls) caught only 0.3% of 1,500 flips of a 98,112-byte shard in the final review, while 63.7% decoded to different candidates with no error (27.5% on an 8-row, 3,248-byte shard). Fix of 2026-11-08: `ShardStore.write` stores the SHA-256 of the shard's content in the file's key-value metadata (`rinchen.content_sha256`) and `ShardStore.read` recomputes it from the decoded rows (a mismatch, a missing digest or an unreadable metadata block is an invalid shard, which is regenerated). Every single-bit flip of the shard file, through `ShardStore.load`: all 9,888 flips of a 1,236-byte shard (941 caught by the digest, 4,136 unreadable, 249 structural, 4,561 left the rows unchanged), all 26,712 of a 3,339-byte shard (7,461 digest, 11,046 unreadable, 232 structural, 7,972 unchanged) and 3,000 random flips of a 98,203-byte shard (1,843 digest, 1,117 unreadable, 8 structural, 32 unchanged): none decoded to different rows without an error. The same harness with the digest comparison switched off decoded 1,840 of those 3,000 to different candidates. Still open: an allocation abort cannot be caught (bit 0 of byte 63 of the 1,236-byte file and bit 0 of byte 66 of the 3,339-byte file abort the process with SIGABRT, return code -6; the committed sweep test works on the 1,236-byte shard and flips bit 1 of byte 63, never bit 0), and the digest is not a signature (whoever can rewrite a shard can rewrite its digest). The crash cases, a partial write or a truncation, were already caught. |
| D-CT2-NUMHYP | guarded in config (found 2026-11-07) | `ctranslate2.Translator.translate_batch(source, beam_size=B, num_hypotheses=N)` raises `ValueError: The number of hypotheses cannot be greater than beam_size * patience` when `N` exceeds `B * patience`; `patience` defaults to 1 and `beam_size` to 2 in the 4.8.4 signature. Reproduced on CPU with the tiny converter model of a D5 test run (`/tmp/pytest-of-tsee/pytest-1030/converter_ct20/model`): `(B, N) = (4, 4)` returned 4 hypotheses, `(4, 5)` and `(1, 2)` raised the error, `(2, 1)` returned 1. The error arises at the first batch, so a long run would end late. Guard: `Ct2Config` rejects `n > beam_size` when the config is loaded. Not verified: the same rule with a `patience` other than 1 (the client never sets it). |
| D-POLARS-SIGINT | workaround in the D6 client only (found 2026-11-08, final review) | Once `polars` is imported, a SIGINT sent to the process does not wake the main thread's blocking `concurrent.futures.wait()` (an untimed lock acquire): the Python handler runs only when the call returns by itself. With polars imported the process's C-level SIGINT handler differs and carries `SA_RESTART` (`sigaction` flags 0x14000004 with polars, 0x0c000000 without, x86_64 Linux, read through `ctypes`), so the kernel restarts the untimed wait after the signal; a wait with a timeout is not restarted. Probe (`ThreadPoolExecutor`, 2 workers, six 1-second tasks, `os.kill(os.getpid(), SIGINT)` from a timer thread at 0.30 s): bare `wait()` is interrupted after 0.30 s with nothing imported (also with numpy, torch, eole, ctranslate2 and sentencepiece imported, per the review's `probe_bisect.py`) and **not until it returns on its own, 3.00 s, once polars is imported**; `wait(timeout=60)` and `wait(timeout=5)` are interrupted after 0.30 s with polars imported. Through the real binary (`rinchen synth run --no-qe`, a loopback server that sleeps 1 s per request, `concurrency` 4, 40 texts in one shard, SIGINT 4.5 s after the start): before the fix exit 130 came 6.33 s after the signal with 40 of 40 requests received by the server (the review measured the same: 6.3 s, 40 of 40); after it, exit 130 came 0.27 s after the signal with 16 of 40 received (the 4 in flight finished, the queue was cancelled; five repeats by the re-review gave 0.77 to 1.06 s, the bound being one request in flight). Workaround: `rinchen.synth._chat_completions._fan_out` waits in slices of 0.2 s (`_INTERRUPT_POLL_S`) instead of one untimed `wait`, and `test_a_real_sigint_cancels_the_requests_still_queued` sends a real SIGINT (it fails by assertion with the bare wait: 3.01 s, all 20 requests sent). Not fixed outside D6: every `rinchen` command whose main thread blocks without a timeout (a lock, a join, `Queue.get()`, an untimed `Future.result()`) is affected the same way, so Ctrl-C is not delivered until the call returns; D4 and D5 commands were not examined. In D6 the remaining untimed blocks are the executor's join at the end of a call and, after a failure, `future.result()` on an earlier request still in flight, which waits for the requests in flight by design (`shutdown(wait=True)`): a second SIGINT sent 1.0 s into two 3 s tasks, after the first had interrupted the polled wait, is raised out of that join at 1.00 s without polars and only at 3.00 s with it; a call into a C++ extension was not examined. |
