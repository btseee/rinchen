# D11 Export, Quantization, Serving, CLI and Package Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a checkpoint of ours runnable: the export directory with its own record (`rinchen.json`) and a quantisation chosen at conversion; the engine that reads it with the guards CTranslate2 lacks (end token, source limit, tag check, reserved symbols, script suppression); the Python class `rinchen.Translator`, the command `rinchen translate` and the service `rinchen serve` (FastAPI, micro-batcher, Prometheus text, a graceful stop that drains); the CPU container recipe; and the gates: strict Eole/CTranslate2 parity, the int8 quantisation gate, the script-masking gate, the serving gate (the STOP gate, as far as it can be proven without building an image).

**Architecture:** `export` owns the record, the reader (`verify_export`, moved out of `train`), quantisation and `convert`; `infer` owns the source-token and reserved-piece rules (moved out of `train`, shared with D10's teacher), script masking, the `Engine` and the `Translator` facade; `train/export_parity` drives Eole for the strict parity; `serve` holds the schemas, the metrics, the micro-batcher and the app; `config/serve` and `configs/serve/*.yaml` the settings; `cli/{export,translate,serve}` the commands; `docker/` the CPU recipe. D10's export code is re-pointed onto the new package (one format, no second reader).

**Tech Stack:** Python 3.14.10, Eole 0.6.4 (subprocess only), CTranslate2 4.8.4 (Python API, CPU), sentencepiece, FastAPI 0.162.0 + Starlette 1.10.0 + uvicorn 0.54.0 + httpx 0.28.1, prometheus-client 0.26.0, pydantic 2.14.1 + pydantic-settings 2.16.2, structlog, typer, polars, pytest + hypothesis. No new dependency.

Spike evidence: `.superpowers/sdd/2026-11-09-d11-export-serving/spike-findings.md` (every number and CTranslate2 or FastAPI fact the code relies on is there, with the script that measured it; read it first). ## Open questions, recorded as such

What the toy cannot answer, and where the code leaves room:

1. **GPU everything.** CTranslate2 on CUDA, `float16` and `int8_float16`, token batching, the speed of a 1.1 B teacher and a 190 M server student, replica memory, the best `inter_threads` and `intra_threads`, the cost of `retry` and of a 30,000-entry suppression list at real size. `--device cuda` is validated and passed through, never run.
2. **The real quantisation loss and parity margin.** The toy saturates at chrF 98.2 (int8 +0.06) and its float32 delta is 1e-6; a real model's int8 chrF drop, whether a quantised real model keeps float32's greedy output, and the float32 margin are unmeasured. The 1.0 and 1e-3 thresholds are the master plan's.
3. **Whether a hard script mask helps a real model.** The toy's leaks come from requests it was never trained for; real leaks, the loss of legitimate Latin names in Cyrillic output under `always`, the purity floor 0.98 and the policy for the other eight languages (the registry's) are priors.
4. **Docker.** The image build, its size (the torch family is skipped by name: the saving is arithmetic from `du` of this repository's environment), its start time, `docker compose up`, the base and uv image tags, a health check and a SIGTERM inside a container, a model-volume layout for a real deployment, a GPU image. The static checks and the native run of the compose `command` stand in for them.
5. **Documents.** Throughput (one CTranslate2 call per window), joiners beyond a space, the `tgt` placement (D9 built `src` windows only), document quality of a real model.
6. **Start-up cost of the command.** `rinchen translate` pays 1.0 to 1.2 s of imports because `rinchen.cli.main` loads every command; lazy command loading is not built. A serving image that also skips Eole, transformers and the data tools needs an extras split of `pyproject.toml`, which D11 does not make.
7. **Languages and directions.** Directions are derived from the saved config's corpus names (a checkpoint not written by our launcher needs `--direction`); zero-shot pairs are allowed and flagged, never judged; auto-detection of the source is the script hint only.
8. **Concurrency limits of the service.** One process; the batcher's `max_wait`, `max_batch_sentences` and queue limit are toy priors; no per-client rate limit, no authentication (a gateway is assumed); no hot reload.
