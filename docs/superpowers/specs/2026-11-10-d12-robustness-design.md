# D12 Robustness: design

Status: binding for the D12 plan (`docs/superpowers/plans/2026-11-10-d12-robustness.md`), written before the build; the last task of the plan amends it to the finished code (section 7, amendments, as D10's section 8 and D11's section 7). The runbook is `docs/runbooks/12_robustness.md`. Master plan: `docs/research/2026-10-29-rinchen-dev-agent-prompt.md`, milestone D12 (and D13, D15 for what D12 must leave room for). Evidence for every fact about the engine, the toy, the metrics and the costs: `.superpowers/sdd/2026-11-10-d12-robustness/spike-findings.md` (a spike on this machine, Eole 0.6.4, CTranslate2 4.8.4, CPU, toy data; scripts and logs named there; the finding numbers F1 to F15 are cited below). Everything GPU-side is unmeasured and labelled so.

## 1. Goal and non-goals

Goal: say, with numbers that can be recomputed from files, how a model of ours behaves on the inputs that break translation systems quietly: numbers, dates and amounts (value and format), placeholders (`⟦0⟧` to `⟦99⟧`), names, glossary terms, the script of the output, and a source written in the traditional Mongolian script. D12 builds the six metrics as pure functions of (source, reference, hypothesis) triples; the suite file that carries the triples and their annotations; a runner that asks an `Engine` for the hypotheses (or reads them from a file); the result `robustness.json` with one outcome per row; the command `rinchen eval robustness` with its manifest; a narrow report `report.json` whose `robustness` block is what D13's and D15's reports embed; a deterministic toy that a tiny model can be trained on in 190 s so that the metrics are measured on a real binary; and the gate. STOP gate (master plan: "robustness block populated in tiny report"): through the real `rinchen` binary on the CPU with the GPU hidden, a tiny model trained for the purpose is run over a generated suite and `report.json` holds all six values, each at or above the named floor of T18 (numbers 0.90, placeholders 0.99, entities 0.90, terms 0.99, script purity 0.999, `mn_Mong` retention 0.95), while the negative controls (hypotheses paired with the wrong rows, the D11 teacher that never saw a digit or a placeholder, a glossary the model never writes, placeholder indices it never trained, the script mask `off`) score far below, so the gate cannot pass vacuously.

Non-goals:
- No mechanism. No placeholder masking or unmasking (`infer/placeholders.py`), no terminology engine (`infer/terminology.py`, constrained decoding, post-hoc replacement), no `terminology` field in the service's request, no term-tagged training data, no change to `Engine`, `serve` or the reserved-symbol rule (T1). D12 measures what a system does with these inputs; it does not make a system do better.
- No real data and no real model: the toy is templated (F6), so every number tests machinery and ranks nothing. No FLORES+, NTREX or Mongolia-sourced set (D13), no COMET or MetricX, no confidence intervals or significance (D13: the per-row outcomes are what it needs), no model card or hub upload, no runner over many systems (T20).
- No GPU was used and none is claimed (the machine has one the owner did not authorise): every Eole process, converter and CTranslate2 translator of a test or measurement runs with `CUDA_VISIBLE_DEVICES=""` on `cpu`; `--device cuda` exists, is validated and was never run.
- Nothing is fine-tuned or continued from a pretrained model (the toy is trained from random initialisation); no Inner Mongolian data or variety, no Latin-script informal Mongolian (the project's content rules in CLAUDE.md apply to code, tests, docs and messages as everywhere); no tuning on FLORES+ devtest (D12 reads none).

## 2. Findings that bind the design (spike)

1. The existing toy has no digit and no placeholder: the Eole vocabulary of its models holds none of the ten digits (344 entries), so a model trained on it cannot read or write one; through the real engine `The price is 1,250.50 dollars.` gives `Тэнд өдөр байна.` with status `ok` and purity 1.0 (F1). The engine's statuses cannot see this class of failure.
2. `⟦n⟧` are single SentencePiece pieces and all 100 are in every export's vocabulary (the D9 invariant); the engine passes them (F1, F3). A model copies one only for the indices it was trained on: `⟦0⟧` to `⟦9⟧` trained, `⟦10⟧` and up (7 of 7 probed) become a random noun (F2). The D11 teacher copies 0 of 400 placeholder rows and keeps 0 of 840 numbers (F2, F7).
3. The engine REFUSES `<t>`, `</t>`, `<r>`, `</r>` in a request (a `RequestTextError`); no model was trained with them and no training mix holds a placeholder or a term marker (F3).
4. `normalize` turns NBSP into a plain space before the model sees a source (F4); the model learns the separator its data used.
5. D4's digit multiset accepts 15 of a toy model's 67 wrong number rows (transpositions, a lost decimal point) and rejects none a value comparison accepts; a copy-through system is value-exact on 960 of 960 rows and surface-exact on 568 (F5).
6. A toy that carries numbers, placeholders, entities and traditional-script sources (25,520 training rows, SentencePiece 800 pieces, 2/2 layers d64, 6,000 steps) trains in 185 to 193 s, is byte-identical across two trainings (same `model.bin` SHA-256), and measures: numbers 0.9323, placeholders 0.9983, entities 0.9313, terms 1.0, retention 0.9976, purity 1.0 at beam 4; beam 1 gives placeholders 1.0 (F6, F7).
7. The controls collapse as they must: rotated hypotheses score 3/960 numbers, 2/600 placeholders, 10/480 entities, 1/1,044 terms, retention 0.06; a glossary the model never writes 0/1,044; script mask `off` leaves 110 of 500 untrained requests below the 0.98 floor (mean 0.9098) and `retry` or `always` none; the D11 teacher leaves 96 of 500 (mean 0.8897) (F7, F8).
8. The engine has no source-side conversion; D5's converter can convert either way but the engine uses it for outputs only; the D5 tiny converter restores 5 of 37 toy nouns, so a converted source arm measures the converter; the direct arm of a model trained on converted rows retains 1.003 of the Cyrillic arm and the D11 teacher's 0.317 over the same 480 rows (F9, F7).
9. The metrics cost 0.1 s per 1,000 rows next to 0.12 s (beam 1) or 0.25 s (beam 4) for the engine; the toy's training dominates everything (F10).

## 3. Rulings

T1. Scope: D12 measures and builds no mechanism. The master plan's D12 line is "eval/robustness.py suites ... Tests first: each metric on synthetic hypotheses with known answers". The master plan's serving pipeline (placeholders, terminology) and D11's spec T22 ("the request schema gains `terminology` there") assumed more; D12 does not take it, for these reasons. (a) No model has ever been trained with a placeholder or a term marker, so a masking feature would destroy the translation of every existing export (finding 2: 0 of 400). (b) A model copies only the indices it trained on (finding 2), which is a training-data requirement that `train/mixture.py` and D6 to D10 do not meet. (c) The inline term form cannot even be sent: the engine refuses the symbols (finding 3) and D11's rule is deliberate. (d) A request field that is accepted and ignored is a silent drop, the class of defect the D10 and D11 reviews found most often; the schema keeps refusing `terminology` with a 422. So `TranslateRequest.terminology`, `infer/placeholders.py` (`mask`, `unmask`, the failure policy) and `infer/terminology.py` stay unbuilt and have no owner after D12 (section 6, item 1); what D12 leaves is the instrument that tells a later builder whether the mechanism works (T5, T7). The edits to existing code are two: D4's numeral folding moves (T16) and the `rinchen eval` stub gains a command (T14).

T2. What a number is. `numbers_in(text, lang=None) -> tuple[NumberToken, ...]` (module `rinchen.eval.robust_numbers`). The text is folded by `rinchen.text.numerals.fold_numerals` (every Unicode decimal digit to ASCII, every run of CJK numerals to its digits, D4's rules, T16) and every `⟦n⟧` placeholder is replaced by a space first (a placeholder index is not a number). A numeric RUN is a maximal span (no digit before or after it) of one of: digits in groups, `\d{1,3}` followed by one or more groups of one space-like separator (U+0020, U+00A0, U+202F, U+2009) and exactly three digits, or a plain digit string; then any number of `[.,:/-]` each directly followed by a digit and more digits. Inside a run: a `:`, `/` or `-` always splits (so `10:30` is 10 and 30, `2024-03-12`, `03/12/2024` and `12.03.2024` are the components 2024, 3 and 12 in their written order, `5-6` is 5 and 6); a space-grouped head followed by `.` or `,` and digits is one decimal number; for a piece with `.` and `,`: both kinds present: the LAST is the decimal point if the other kind groups threes (`1,250.50`, `1.250,50`), else the run is not a number and its digit groups are separate numbers; one kind repeated: grouping if the first part has one to three digits and every other part exactly three (`1.250.000`), else separate numbers (`10.0.0.1`, `1.2.3`); one separator once: a decimal point, unless exactly three digits follow it and the part before has one to three digits without a leading zero, which is the ambiguous case of T4. A value is a `Decimal`; leading zeros do not matter (`03` equals 3, `0,500` is 0.5). A `-` or U+2212 directly before a single-number run, preceded by the start of the text, a space or `(`, makes the value negative. `unit` is the currency symbol (`₮`, `$`, `€`, `£`, `¥`, `₽`, `₩`, written with `chr()` in code) directly before or after a single-number run, with at most one group-space between; `%` is not a unit. `surface` is the number as written after folding (group spaces normalised to U+0020), kept for the format figure. At most 65 tokens are produced per text (a runaway text); the matcher uses the first 64 and counts the overflow as extra. Limits, recorded as such: number words (`three`, `гурав`), magnitude words (`сая`, `million`), `1e5` (1 and 5), a leading-dot decimal (`.5` is 5), `10.30` as a time (a decimal 10.3), digits glued to letters (`COVID-19`, `A4`: counted), ordinals (`3-р` is 3).

T3. `numbers_acc`. The unit is a row of the `numbers` section; the expected numbers are those of the REFERENCE (what a human wrote in the target language), parsed under the row's `tgt_lang`. A row is SCORED when the reference has at least one number and the source's numbers (parsed under `src_lang`) match the reference's one for one (`numbers_agree`: equal counts, every reference token matched by a source token with an intersecting reading); otherwise it is EXCLUDED and counted under its reason (`no_numbers`, `source_reference_disagree`), never dropped silently, and the suite builder of the toy emits no excluded row (a test). For a scored row the reference tokens and the hypothesis tokens (parsed under `tgt_lang`) are matched one to one by a maximum bipartite matching on intersecting readings (Kuhn's algorithm, reference tokens in order, hypothesis tokens in order; deterministic): `expected` is the reference's count, `found` the matched pairs, `extra` the unmatched hypothesis tokens, `units_ok` is true when every matched reference token that has a unit meets a hypothesis token with the same unit (an expected unit-less token accepts any unit), and the row is `exact` iff `found == expected`, `extra == 0` and `units_ok`. Order never matters (a date may change layout between languages; `5 and 7` equals `7 and 5`); a missing, extra or changed number, a lost decimal point or a transposed digit fails the row. `numbers_acc` is `exact` rows over scored rows. Beside it, as details: `recall` (sum of `found` over sum of `expected`), `extra_tokens`, `surface_exact_rows` (the multisets of `surface` strings equal: the FORMAT also matches), `unit_failures`, `ambiguous_rows`, `capped_rows`. The suite's `category` (`int`, `decimal`, `grouped`, `percent`, `currency`, `date`, `time`, `two_numbers` in the toy) gives the breakdown. A source without numbers is out of the section, not a pass: with no scored row the value is `null`, never 1.0. Why the value and not the surface: a copy-through system is value-exact on 960 of 960 toy rows and surface-exact on 568 (finding 5), and references of real data write `3.5` and `3,5` alike; the surface figure keeps the format question visible without making it the headline.

T4. Conventions and the ambiguous group. One separator followed by exactly three digits (`1,250`, `1.250`) is a decimal or a grouping. The language of the TEXT decides when it is known: English, Chinese, Japanese and Korean (`eng_Latn`, `zho_Hans`, `jpn_Jpan`, `kor_Hang`) write `.` for the decimal and `,` for grouping (`1,250` is 1250, `1.250` is 1.25); Russian, German, Turkish and Kazakh (`rus_Cyrl`, `deu_Latn`, `tur_Latn`, `kaz_Cyrl`) the reverse (`1.250` is 1250, `1,250` is 1.25); Khalkha, traditional Mongolian and an unknown language (`khk_Cyrl`, `mn_Mong`, `None`) are MIXED: the token carries both readings and is flagged `ambiguous`, and it matches a token that shares either. The table is a prior (Mongolian text mixes both conventions in practice and the project has no corpus statistic); the flag makes the exposure visible (`ambiguous_rows`), and the one false accept it allows is a reading the source itself allows. Surface differences between languages are never an error of value (`3.5` equals `3,5`, `1 250,50` equals `1,250.50`).

T5. Placeholders. Module `rinchen.eval.robust_placeholders`. A placeholder is the glyph pair of `spm.symbols` around one or two digits without a leading zero, index 0 to 99 (the pattern is built from `user_defined_symbols()[-PLACEHOLDER_COUNT:]`, and a test checks that it matches each of the 100 symbols exactly and nothing else). `placeholders_in(text)` lists the indices in order; `damaged_brackets(text)` counts the glyphs of the pair that are not part of a well-formed token (`⟦ 3 ⟧`, `⟦3`, `3⟧`, `⟦03⟧`, `⟦100⟧`). The unit is a row of the `placeholders` section whose SOURCE holds at least one placeholder (`no_placeholders` otherwise) and whose reference holds the same multiset (`source_reference_disagree` otherwise). A hypothesis is `exact` iff its multiset of indices equals the source's (every placeholder present exactly as often as in the source, no foreign one) and `damaged_brackets` is 0; details: `missing`, `extra`, `damaged` (sums), `exact_rows`, `order_ok_rows` (exact rows whose order equals the REFERENCE's order: order is legitimately free across languages, the genitive template of the toy reverses two placeholders, so it is a detail and never part of the value). `placeholder_acc` is `exact` over scored rows. It is measured on the engine's RAW output: a repair policy ("missing: append the original span") would make every row pass by construction and measure nothing, so D12 builds none (T1). The suite is built from the toy by replacing the nouns of the base templates (and a genitive template) with placeholders in both sides; the indices a toy model copies are the ones it trained on (finding 2): the gate's rows use 0 to 9 and a control uses indices it never saw. What a placeholder stands for (a number, a URL, a tag, a name) is irrelevant to the metric, which only asks that the token survives once; the toy masks nouns, a real builder would mask spans.

T6. Entities. There is no NER: an entity is an entry of the suite's ENTITY TABLE, `id -> language -> accepted spellings` (the first is the one the toy writes; English may list two, `Ulaanbaatar` and `Ulan Bator`), and a row of the `entities` section lists the ids it expects in the hypothesis, written in the row's `tgt_lang`. A spelling is PRESENT in a text when, after NFC and casefolding of both, it occurs at a boundary (no letter, mark or digit directly before it; internal spaces match any run of spaces) followed by at most 4 letters (a case suffix: Khalkha `Улаанбаатарт`, `Улаанбаатараас`; Russian `Улан-Баторе`; English `'s` is a non-letter) and then a non-letter, mark or digit (finding 11). The 4 is a prior; a short name is a prefix of a longer one (`Бат` matches `Батор`), a known over-acceptance. The unit of `entity_acc` is a MENTION (an entity id of a row), found or not, so a row with two names counts two; `entities.details.rows_all_found` gives the strict row view, and every row outcome carries `expected` and `found`. An id listed twice in a row, an id missing from the table, a table entry without a spelling for the row's `tgt_lang` or with an empty spelling is a `DataError` when the suite is read. Transliteration (Cyrillic, Latin, Russian) is only what the table lists: no rule maps `Улаанбаатар` to `Ulaanbaatar`. Real data has no table, so on D13's sets `entity_acc` is `null` (section 6, item 4).

T7. Terminology: the metric and the baseline, no mechanism. A row of the `terms` section lists pairs `(src, tgt)`: a glossary entry whose source term occurs in the row's source (`span_present`, the rule of T6; otherwise the mention is excluded as `absent_in_source`) and whose required target term must be present in the hypothesis (the same rule). `term_acc` is found mentions over scored mentions. What it measures today is the UNCONSTRAINED model against a glossary: the toy gives 1.0 for a glossary made of the model's own nouns and 0 of 1,044 for a glossary of words it never writes (finding 7), which is the headroom a constraint mechanism has to close; the second glossary is a control suite, never part of the headline. The metric is the one the master plan names (`term_acc`); the mechanism (inline `<t>src</t><r>tgt</r>` in a model trained with term rows, else post-hoc replacement) is T1's open item.

T8. Script purity. Module `rinchen.eval.robust_script`. The unit is a row of the `script` section: `(source, src_lang or null, tgt_lang, script)` with `script` `Mong`, `Cyrl` or `null` (a script is allowed only when `tgt_lang` is `khk_Cyrl` or `mn_Mong`, as the engine's request is). The scripts a row's output must be in are `allowed_scripts(effective)` where `effective` is `mn_Mong` when `script` is `Mong`, `khk_Cyrl` when it is `Cyrl` and the registry's scripts of `tgt_lang` otherwise. The row's purity is `infer.script_mask.script_purity(text, scripts)` (the share of its counted letters in them); a text with no counted letter (empty, or only digits, punctuation, placeholders) has purity `null`, is EXCLUDED as `no_letters` and counted: unlike `script_purity`, which gives 1.0, a robustness figure must not count silence as pure. `script_purity` (the block's value) is the MEAN purity over the scored rows; details: `min`, `pure_share` (the share at or above `PURITY_FLOOR` 0.98, D11's prior), `below_floor`, `no_letters`, `floor`. The mean is chosen because the floor is a prior and the mean moves smoothly; `below_floor` is the figure that says how many outputs a decode check would have retried. The suite's rows are requests that provoke a leak: the trained directions (`trained`), pairs the model never trained with `src=None` (`untrained`, the D11 gate's five pairs), and, in a separate suite, the converter's traditional-script output (`Mong`). Run under the default mask `retry` the toy scores 1.0; under `off` 110 of 500 untrained requests fall below the floor (mean 0.9098), and the D11 teacher 96 (0.8897) (finding 7): the section can fail, which is its point.

T9. The `mn_Mong` source. Module `rinchen.eval.robust_mong`. A row of the `mong` section has the Khalkha Cyrillic `source` (`src_lang` `khk_Cyrl`), the same sentence in traditional script `source_mong`, a `reference` in `tgt_lang`. The runner makes up to three requests per row, the ARMS: `cyrl` (the control: `source` as `khk_Cyrl`), `mong` (`source_mong` as `mn_Mong`: the master plan's "mn_Mong source passes through script tag": the model reads the script itself) and, only when a script converter is attached, `converted` (`converter.convert(source_mong, "Cyrl").text` as `khk_Cyrl`). `mong_source_retention` is the corpus chrF of the `mong` arm over the corpus chrF of the `cyrl` arm, both against the references (`metrics.bleu_chrf.corpus_scores`, sacrebleu defaults), not clipped (1.003 is possible); `null` when the Cyrillic chrF is 0. Details: `chrf_cyrl`, `chrf_mong`, `agreement` (rows whose two arms wrote the same text), `chrf_converted` and `retention_converted` (`null` without a converter), `rows`. The row outcome's `ok` is that the two arms agree and `value` the sentence chrF of the `mong` arm. The toy trains on `converted`-origin rows and so retains 0.9976; a model that never saw the script retains 0.317 (finding 8); the D5 tiny converter makes the converted arm 0.562 (it restores 5 of 37 toy nouns): the arm measures the converter, which is why it is optional and reported beside the direct one. Whether a production model should read the script itself or be fed a conversion is a product decision this instrument informs and does not make (section 6, item 6).

T10. The six values and the contract. `robustness_block(result)` returns exactly `{numbers_acc, placeholder_acc, term_acc, script_purity, entity_acc, mong_source_retention}`, each a float or `null` (the section is absent, or has no scored row). The master plan's contract (`rinchen.eval/1`: `robustness: {numbers_acc, placeholder_acc, term_acc, script_purity}`) has no slot for two of the suites its own D12 item lists; D12 AMENDS it to these six keys (amendment C1): the four named keys keep their names and their meaning, `entity_acc` and `mong_source_retention` are added. D13 composes `result.json` and embeds the block as it is. A `null` is shown as `n/a` by a reader and never as 0 or 1.

T11. The suite file. A JSON document, schema `rinchen.robustness.suite/1`, UTF-8, `ensure_ascii` off, sorted keys, two-space indent, one final LF, the rows in the order the builder gave them: `{schema, name, entities: {id: {lang: [spellings]}}, sections: {section: [row]}}`. Sections, all optional, at least one non-empty: `numbers`, `placeholders`, `entities`, `terms`, `script`, `mong`. A row: `id` (`[A-Za-z0-9._-]{1,64}`, unique within its section), `src_lang` (a registry code; `null` only in `script`), `tgt_lang` (a registry code), `source` (non-empty), `reference` (required in `numbers`, `placeholders`, `mong`; optional, `null` allowed, elsewhere), `category` (`[a-z0-9_]{1,24}`), and per section `entities: [id]` (`entities`), `terms: [{src, tgt}]` (`terms`), `script: "Mong" | "Cyrl" | null` (`script`), `source_mong` (`mong`, with `src_lang` `khk_Cyrl`). The reader (`Suite.from_bytes`) is as strict as `ModelRecord.from_bytes`: exactly these fields and no other, each of its type, a repeated key refused (an `object_pairs_hook`), duplicate ids refused, a text of more than 2,000 characters or with a lone surrogate or with a reserved symbol of the project other than a numbered placeholder (`source_symbols()`: the engine would refuse the whole batch) refused, `DataError` naming the section, the row id and the field and never quoting a text; the file is at most 8 MiB. The file is read once: `read_suite(path)` returns the suite and the SHA-256 of the bytes it parsed. LOCATION: suites are GENERATED deterministically at test time from `tests/support/robust_toy.py` into `tmp_path` (the toy is seeded: the same seed gives the same bytes), not committed; only a hand-written golden suite and golden hypotheses (about 40 rows, under 50 KB) live in `tests/fixtures/robustness/`, with known answers for every metric; the repository's fixtures stay under the 2 MB total. D15's tiny pipeline has its own fixtures (`tests/fixtures/parallel`) and builds its own suite with the same format (section 6, item 7).

T12. Requests, hypotheses, the runner. `suite_requests(suite)` lists the requests in a fixed order (sections in the order above, rows in file order, arms `cyrl`, `mong`, `converted`): a `Request` is `RequestKey(section, id, arm)` with `arm` `main` for every section but `mong`, the text, the languages and the script. `Hypothesis(text, status)` with the engine's statuses (`ok`, `empty`, `too_long`, `truncated`, `no_output`; a hypotheses file may omit `status`, which then reads `ok`). `run_requests(requests, engine, options) -> dict[RequestKey, Hypothesis]` makes ONE `engine.translate` call with `Row(text, src_lang, tgt_lang, script)` and returns one hypothesis per request, in order, never fewer (a mismatch is an `UpstreamError` naming the counts); the engine is any object with `translate(rows, options)` (`Engine` fits, so do the fakes of `tests/support`). A non-`ok` status is not an error: the text (possibly empty or partial) is scored as it is and the status counts per section appear in the result (`statuses`), so a failure the engine itself flagged is visible beside the metric. The engine's own all-or-nothing errors stand (a target the model cannot write and no converter makes: `ConfigError`, exit 2). A hypotheses file is JSON Lines, one object per request with the keys `section`, `id`, `arm`, `status`, `text`, sorted keys, `ensure_ascii` off; reading it takes the SHA-256 of the bytes once and parses those bytes, refuses a missing request, an unknown request and a repeated one (`DataError` naming section, id and arm, never a text); the runner writes the same format (`hypotheses.jsonl`), so a run can be rescored, and a baseline system's output (D13's NLLB, MADLAD, Hy-MT2) enters through the same file.

T13. The result. `compute_robustness(suite, hypotheses, *, system) -> RobustnessResult`; `robustness.json` is schema `rinchen.robustness/1`, sorted keys, two-space indent, LF, no timestamp (the same inputs give the same bytes). Layout: `system: {name, model_sha256 | null, manifest_sha256 | null, options | null}` (a model run records the engine's `info` hashes and the decode options; a hypotheses run records nulls), `suite: {name, sha256, rows: {section: n}}`, `robustness: {six values}`, `sections: {section: {unit ("row" | "mention"), rows, scored, excluded: {reason: n}, ok, value, details: {...}, by_category: {category: {scored, ok}}, by_direction: {"<src>-<tgt>": {scored, ok}} (`und` for a null `src_lang`), statuses: {status: n}}}` and `rows: {section: [{id, category, direction, scored, reason, ok, expected, found, value}]}`. `ok` and `scored` are rows, or mentions for `entities` and `terms`; `value` is the headline of the section (accuracy, mean purity, retention) or `null`; the row fields that do not apply are `null` (`expected` and `found` are the token or mention counts of the numbers, placeholders, entities and terms rows; `value` the purity of a script row and the sentence chrF of a `mong` row). Floats are written as Python writes them, rounded nowhere. The per-row outcomes are for D13's paired bootstrap: a resample of rows gives a resampled `ok` count. The numbers and the placeholders are rows, the entities and the terms mentions, the script a mean, the `mong` section a corpus ratio; each section says which in `unit` and `details`.

T14. The command. `rinchen eval robustness --suite FILE (--model DIR | --hypotheses FILE) --out-dir DIR [--system NAME] [--beam-size 4] [--max-decoding-length 256] [--script-mask retry|always|off] [--device cpu|cuda] [--threads 1] [--script-converter-ct2 DIR --script-converter-spm FILE]` (the converter options as `rinchen translate`'s, both or neither, only with `--model`; `--model` also reads `RINCHEN_MODEL`). It hashes the suite (and the hypotheses file) before parsing and reads the bytes it hashed (`hash_input`, then `verified_content`), makes `verify_export` vouch for the model (a directory our manifest does not vouch for is exit 2, and nothing is written), refuses a foreign manifest in the output directory and an output directory that is an input's, removes the old manifest and results just before it writes (`begin_commit`), writes `robustness.json`, `report.json` (T15), `hypotheses.jsonl` (with `--model`) and, LAST, `manifest.json` (stage `eval_robustness`; inputs: the suite, the hypotheses file or the five files and the manifest of the export, the converter's files when attached, each with the digest taken before any read; outputs: the files written; metrics: the non-null values of the six and `rows.<section>`; status: `robustness: ok`, `mode: model | hypotheses`, `script_mask`; packages `ctranslate2`, `sentencepiece`, `sacrebleu`, `regex`; seed -1; `config_sha256` of the canonical JSON of the options). The command MEASURES: it has no threshold, no pass or fail, and exits 0 when it measured (the floors are the gate's). It prints `suite: <name>`, `system: <name>`, one line per section (`numbers: 0.9323 (895/960), excluded 0`, `n/a (no scored row)` for a null), `result: <O>/robustness.json`, `report: <O>/report.json`, `manifest: <O>/manifest.json`. Exit codes: 2 a bad option, both or neither of `--model` and `--hypotheses`, an export that is not vouched for, a refused device or compute option, an unusable `--system`, a target the model cannot write; 3 an unreadable or invalid suite or hypotheses file, another stage's manifest in the output directory; 4 CTranslate2 failed; 1 the output cannot be written; 130 interrupted. A message never quotes a text of the suite or of a hypothesis (a reviewed AST scan, as D11's). The model is opened before anything is written; `--device cuda` is validated and never run here; `auto` is refused as everywhere.

## 5. Tests and the gate

- Unit tests per metric with hypotheses of KNOWN answers (the vectors of the plan, computed with `spike/scripts/numbers_ref.py` and the span and placeholder rules), every edge case of T2 to T9 named in the plan (repeated numbers, order, partial matches, Unicode digits, group separators, units, signs, empty hypotheses, no numbers in the source, ambiguous tokens, a runaway hypothesis); property tests (hypothesis library) for the number extractor (never raises, deterministic, a text matches itself, no digits means no tokens), the span matcher and the suite reader (a round trip, one mutated byte refused); layering and message scans; the golden suite and golden hypotheses of `tests/fixtures/robustness/` give an exact `robustness.json` (a golden file) so that the schema is pinned.
- The command with a fake engine (`tests/support/translate_cli.py` style): every option, every exit code, nothing written when the model is refused, the foreign manifest, the manifest written last, the same inputs give the same bytes, no text in any message.
- The gate (T18, `subprocess` marker): the toy trained once per session (190 s), the command run through the real binary over the generated suites, the negative controls above. A miss of a threshold is answered by raising the steps of the toy, never by lowering the threshold.
