# D14 Maintenance loop: design

Status: binding for the D14 plan (`docs/superpowers/plans/2026-11-11-d14-maintenance.md`), written before the build; the last task of the plan amends it to the finished code (section 7, amendments, as D12's and D13's). The runbook is `docs/runbooks/14_maintenance.md`. Master plan: `docs/research/2026-10-29-rinchen-dev-agent-prompt.md`, milestone D14 (and D15 for what D14 must leave room for). Evidence for every fact about `uv`, `uv.lock`, the doctor, pytest, the parity commands, the costs and the workflow draft: `.superpowers/sdd/2026-11-11-d14-maintenance/spike-findings.md` (a spike on this machine, CPU, offline; the finding numbers F1 to F18 are cited below). Everything GPU-side, everything on GitHub Actions, the real state of PyPI, the lines `uv` prints for a change, and every real model, corpus or export is UNMEASURED and labelled so.

## 1. Goal and non-goals

Goal: let a maintainer, and a scheduled job, answer three questions about the stack the project stands on from one command, with states that say what was and was not looked at: (1) is this machine the stack the lock file names, and does the toolchain still start (the CPU doctor checks, the lock against `pyproject.toml`, the installed packages against the lock); (2) what could `uv` take next within the constraints of `pyproject.toml`, and which of that does a recorded decision say not to take blindly (the dependency drift table); (3) do the numbers the project pinned with golden tests and parity checks still come out the same (the parity reruns, cheap ones every night, heavier ones every week). D14 builds `rinchen maintain check` and its library `rinchen.maintain`, the configuration `configs/maintain/maintain.yaml` (the pin rules, the reruns and their cadences and bounds), the report `maintain_report.json` with a Markdown summary and a manifest that records every resolved package version and the lock file's SHA-256, `.github/workflows/nightly.yml`, and the runbook `14_maintenance.md` (the upgrade procedure, the rollback, what each failure means). STOP gate (master plan: "nightly workflow green on tiny"): through the real `rinchen` binary on the CPU with the GPU hidden, the command that the nightly workflow runs, read from the workflow file and run natively through a `uv` that never contacts an index, is green on the tiny profile: doctor, lock, environment, the dry-run table from a hand-written sample (labelled), the golden and the Eole-against-CTranslate2 parity reruns on the toy, a report and a manifest that pass the content scans, equal bytes on a rerun, and every control (a failing rerun, an empty selection, a timeout, a bad uv output, a held package) failing as it should. "Green on GitHub Actions" is UNMEASURED: nothing here can run a workflow.

Non-goals:
- No upgrade. Nothing in D14 writes `uv.lock` or `pyproject.toml`, runs `uv lock --upgrade` without `--dry-run`, `uv add`, `uv sync` or `pip`, makes a branch, a commit, a push, a pull request or a merge. An upgrade is an operator's procedure on a branch (M15); the nightly job only reports.
- No view of what exists on PyPI. The drift table is what `uv lock --upgrade --dry-run` would take within the constraints of `pyproject.toml`; a package pinned with `==` (12 of the 38 direct dependencies, among them Eole, CTranslate2, SentencePiece, sacrebleu and torch) never appears in it (F13). `uv tree --outdated` and any PyPI query of our own are not built.
- No GPU, no docker, no model download, no Hub, no token, no secret. The doctor's GPU check is never run (M4). Nothing here reads a token file or a cache directory of another tool.
- No real data and no real model: the reruns run on the toy. The one hook for an operator's export is the `parity_export` rerun (M8); a robustness or evaluation rerun over a real export is not built (D12's command measures and has no floors; its floors are the toy's, F9).
- Nothing the project's content rules in CLAUDE.md exclude: the dependency report lists names, versions and the lock file's hashes and nothing else about a package.
- No automation of `docs/STACK.md` (a hand snapshot, Windows-only, last generated 2026-10-30): the manifest of a check is the machine-readable record, and the runbook says how to refresh the snapshot by hand.
- The older Phase 14 text of the superseded plan (a `/feedback` endpoint, weekly human review of feedback, monthly retraining and a monthly report) is not the master plan's D14 and is not built.

## 2. Findings that bind the design (spike)

- F1 The doctor has 7 checks and 3 states and takes 15.6 s: `D-EOLE-CLI` 10.72 s, `D-CT2-CONV` 2.46 s, the rest under a second; `D-TORCH-CUDA` imports torch and asks CUDA a question (hidden here, but a maintenance command must not depend on that); two messages embed exception text that can hold a path.
- F2 `uv.lock` is TOML that `tomllib` reads in 0.024 s: 187 entries, 186 names (`pyonmttok` twice, one wheel per platform), `version = 1`, `revision = 5`, 182 PyPI entries, 1 `pytorch-cu130` entry (torch `2.14.1+cu130`, a version with a local label), 3 `path` entries and the editable project (no hash); names are normalised already.
- F3 `uv lock --offline --dry-run` on an unchanged project prints `Using CPython <path> interpreter at ...`, `Resolved 187 packages in 1ms` and `No lockfile changes detected` and exits 0; with any change of the requirements it fails offline here (the cache has the Linux resolution only), so **the lines for an update, an add and a remove are UNMEASURED**; the sample of the tests is hand-written and the parser refuses what it does not know. The documentation says upgrades are limited by the project's constraints.
- F4 `uv lock --check --offline` validates the lock against `pyproject.toml` in 0.075 s; `ci.yml` syncs with `--frozen`, which never checks.
- F5 The environment equals the lock on this machine (186 names, 0 differences) and `importlib.metadata` reads it in 0.058 s; "locked, not installed" is legitimate on another platform (markers), "installed with another version" and "installed, not locked" are not.
- F6 `mypy src` 19.4 s, ruff 0.044 s each, collection 3.15 s for 17,853 tests; the full gate 25 min 44 s (D13's record, parallel parts) to 30 min 44 s (D12's, sequential): too long for a nightly job that repeats what `ci.yml` already runs on the same tree.
- F7 The numerics goldens (the sacrebleu statistics and their private API, the bootstrap, D13's golden report, D12's metrics, the 289 normalization goldens) rerun in 4.64 s: 1,110 passed.
- F8 Eole against CTranslate2: `tests/integration/test_export_parity.py` 13 passed in 137.24 s; the real `rinchen export parity` over an existing export 4.06 s (200/200 exact, mean |delta| 7.19e-07); it prints absolute paths and writes `parity.json`.
- F9 `rinchen eval robustness` measures in 2.34 s and has no threshold; the floors are literals of the gate module (31 tests, 388.27 s).
- F10 The evaluation gate modules (99 tests): 99 passed in 384.40 s. F11 The serving gate modules and the engine surfaces (55 tests): 55 passed in 309.78 s.
- F12 pytest: exit 0 all passed, 1 failures or errors, 4 usage error, 5 nothing collected; `--junitxml` gives `tests`, `failures`, `errors`, `skipped` (a deselected test is not counted; skipped ones are inside `tests`); the file holds an absolute path and a hostname that no report may copy.
- F13 12 of 38 direct dependencies are exact pins: the dry run is blind to them and to what they pin; the table is "what uv could take", never "what exists".
- F14 A drift prototype over a MEASURED no-change output, a MEASURED failure and a HAND-WRITTEN change output recognised every line, found every "old" version equal to the lock's and classified `numpy` and `nvidia-cudnn-cu13` by rule.
- F15 A workflow draft reads as data (key `on` is `True`, two cron strings, a `workflow_dispatch` choice input, an expression for the cadence); the actions are `ci.yml`'s versions; everything about GitHub itself is unmeasured.
- F16 `python -m rinchen` runs the same app; `uv --version` is `uv 0.13.7`; `just` is not installed here; `run_logged` hides the exit code a pytest rerun needs.
- F17 `uv run` puts the path of the uv that started it in the environment variable `UV` (`/home/tsee/.local/bin/uv` in the measurement), and `uv run --no-sync --frozen --offline rinchen --help` runs the project's command without touching the environment or the lock (lock SHA-256 unchanged).
- F18 `uv run --project P --no-sync --frozen --offline` run from another directory keeps that directory as the working directory and finds the project's environment (`rinchen.config.loader.REPO_ROOT` is the editable install's root whatever the directory), so a command of the workflow can run in a temporary directory and write its output there.

## 3. Rulings

M1. Scope, names and layering. D14 builds exactly what the master plan's D14 line names plus the seams it needs: `rinchen maintain check` (a typer group `maintain` with one command, registered in `cli/main.py`), the library `rinchen.maintain` (no `cli`, no model, no network library, nothing but the standard library, pydantic, PyYAML and `rinchen.errors` and `rinchen.config.maintain`), the configuration `configs/maintain/maintain.yaml` read by `rinchen.config.maintain`, `.github/workflows/nightly.yml` and `docs/runbooks/14_maintenance.md`. The command only reads: it never writes the lock file or `pyproject.toml`, never runs anything that changes the environment, never runs a model, never opens a socket itself (the one network step of a night, the dry run, is `uv`'s). Reason: a check that can change what it checks cannot be trusted to report it, and the project's rule is that an upgrade is a decision recorded in `DECISIONS.md`. Cost if wrong: an unnoticed write to the lock would make the nightly job a silent upgrader; two tests make it visible (the gate hashes both files before and after every run; a static scan shows no module of `rinchen.maintain` or `cli/maintain*` writes a path named `uv.lock` or `pyproject.toml` or builds an argument list with `add`, `sync`, `pip` or `--upgrade-package`).

M2. The steps, their order and the states. `check` runs, in this order and each once: `doctor` (M4), `lock_file`, `lock_consistent`, `environment` (M5), `drift` (M6, M7), `reruns` (M8). Every step ends in one of four states and a reason: `ok`; `drift` (only the drift step, when its table is not empty); `fail`; `skipped`, whose reason is one of a CLOSED list written once in `rinchen.maintain.states` (pinned by a test): a GPU check that is never run, `disabled by --no-drift`, `disabled by --no-reruns`, `not due at the <cadence> cadence`, `no export was given`, `a doctor or environment check failed`, `reported by the doctor itself`. A step never disappears: an unmeasured thing is a `skipped` with its reason or a `fail` with its reason, never an absence. The steps are all attempted even when an earlier one fails (they are independent) except the reruns, which are `skipped (a doctor or environment check failed)` when the doctor or the environment check failed: their numbers would be about another stack and they cost minutes. The state of a step that holds several items (the doctor's checks, the reruns) is `fail` if any item failed, else `ok` if any item is `ok`, else `skipped`. The state of the whole run is `fail` if any step failed, else `drift` if the drift step is `drift`, else `ok`. Reason: the nightly job needs one word and a table that says why; D15's report vocabulary is "status ok / skipped with a reason" (master plan), and this is its superset. Cost if wrong: a silent drop would read as health; a test asserts the report lists every step and every rerun of the configuration, due or not.

M3. Exit codes. 0: the run is `ok` or `drift` (drift is information, never a failure unless asked). 4: the run is `fail` (a measured result: everything is written and printed, as `rinchen export parity` does) or `--fail-on-drift` was given and the run is `drift`. 2: a bad option, an invalid configuration, a `--rerun` that names no rerun of the configuration, `--export`, `--checkpoint` and `--corpus` not given together, a file that changed after it was hashed, an output directory that is the project's directory or an input's. 3: `pyproject.toml` or `uv.lock` missing or invalid (TOML, a lock format version other than 1, an entry without a name or version), another stage's manifest in the output directory. 1: the output cannot be written. 130: interrupted. Reason: the same numbers as `rinchen export parity` and the other commands of the project; `drift` stays green because with 186 locked packages something is almost always newer, and a job that is red every week is a job nobody reads. Cost if wrong: if drift should wake someone, `--fail-on-drift` is one option away; the workflow does not use it.

M4. The doctor step. The six CPU checks (`D-PY`, `D-WHEELS`, `D-EOLE-PY`, `D-EOLE-CLI`, `D-CT2-CONV`, `D-CT2-IMPORT`) are called in process through the functions of `rinchen.cli.doctor` that exist, in the order of the doctor; `D-TORCH-CUDA` is NEVER called: its row is `skipped` with the GPU reason. The CPU list lives in `rinchen/cli/maintain_doctor.py`; a test pins that the set of check functions of `doctor.ALL_CHECKS` is exactly the CPU list plus `check_torch_cuda`, so a new doctor check forces a decision (CPU or GPU). The report holds the check id and the state; the doctor's message (it can hold an exception text and a path, F1) is printed on standard output for a `fail` and is never written to the report. A doctor check that raises is a `fail` of that check. Reason: the brief and the project's rule that no tool asks CUDA a question; `torch.cuda.is_available()` is harmless only because something else hides the device. Cost if wrong: a new doctor check that asks a device question would run unnoticed; the pin test fails first.

M5. The lock steps. `lock_file`: `uv.lock` is hashed, then parsed with `tomllib` from the bytes hashed (`lock_sha256` is in the report and the manifest); `version` must be 1 (anything else is exit 3: the reader does not guess a newer format) and every entry needs a string `name` and `version`; the report holds the number of entries, the number of distinct names, the format `version` and `revision`. `lock_consistent`: `uv lock --check` through the runner (M10), 120 s: exit 0 `ok`, any other exit or a timeout `fail` (`uv exited with code N`, `timed out after S s`), no `uv` on `PATH` and none given with `--uv` `fail` (`uv was not found`); it matters because `ci.yml` and the nightly job sync with `--frozen`, which never notices a `pyproject.toml` that moved without the lock (F4). `environment`: the installed distributions (`importlib.metadata`, names in PEP 503 form) against the names and versions of the lock: `fail` when an installed package has a version the lock does not list for that name or is not named by the lock at all (an exact sync removes extraneous packages); a locked package that is not installed is only COUNTED (`not_installed`), because the lock holds packages for other platforms (F5); the report lists at most 20 names of each kind, sorted, with a count of the rest. A version is a string compared for equality, never as a number (`2.14.1+cu130`). Reason: three independent ways the stack the other steps measure can differ from the stack the lock names, each cheap (0.075 s and 0.06 s). Cost if wrong: an environment that drifted from the lock would make every later number about another stack; the reruns are skipped when this step fails.

M6. The drift step. The runner (M10) runs `uv` with the arguments of the configuration (shipped: `lock --upgrade --dry-run`, 300 s) with ANSI colour off (`NO_COLOR=1`), no progress bar and `UV_PYTHON_DOWNLOADS=never`; the combined output goes to `logs/drift.log` in the output directory and is read back at most 64 KiB. **The loader refuses any argument list that does not start with `lock`, does not contain `--dry-run`, or holds a flag outside the closed list `--upgrade`, `--dry-run`, `--offline`, `--check`** (so no configuration can make the check write the lock or upgrade one package). The executable is `shutil.which("uv")` or `--uv FILE`; the environment variable `UV` is NOT read (F17: `uv run` sets it to the uv that started it, and the gate relies on a `uv` of its own on `PATH`). A failure to start, a timeout or an exit code other than 0 is `fail`. The parser (`rinchen.maintain.uv_output`) strips ANSI sequences, trims lines and sorts every line into exactly one class: a known boilerplate line (`Using CPython <x> interpreter at: <path>`, `Resolved <n> package(s) in <t>`, `warning: ...`, blank), the positive line `No lockfile changes detected`, a change line (`Update`, `Updated`, `Add`, `Added`, `Remove`, `Removed`, then a name, a version with an optional `v`, and for an update `->` and the new version) or UNRECOGNISED. The outcome is `ok` only on the positive line with no change line; `drift` only when at least one change line parsed and no line is unrecognised; every other case is `fail` (`the output of uv has <n> lines this version does not recognise`, or `uv printed no recognisable result` for an empty output, or a positive line next to change lines). Every parsed `old` version (an update) or `locked` version (a remove) must be a version the lock file lists for that name, and an add must name a package the lock does not hold: any disagreement is `fail` (`uv reported a locked version that differs from uv.lock for <n> packages`). The table's `locked` column comes from the lock file, never from the output. Reason: the format of the change lines is UNMEASURED (F3: the one offline run that could print them fails here); a parser that matched nothing and reported "no drift" would be the worst failure a drift check can have, so recognition is positive, unknown text fails loudly, and a cross-check against the lock catches a mis-parse. The first real nightly run on GitHub (or any online run) is where the format is learned: `logs/drift.log` keeps the real output for the operator, and the plan's open question 1 asks that it be turned into a recorded fixture. Cost if wrong: if the real format differs, the first night is red with `fail` and a count, not green and wrong; fixing it is one regular expression and a fixture.

M7. The classification of the table and the pin rules. Each entry of the table is `{package, change (update, add, remove), locked, available, class, rule, requires}`; the entries are sorted by package then change. `class` is `drift` (nothing says not to take it: take it through the procedure) or `blocked` (a rule matched). The rules are DATA in `configs/maintain/maintain.yaml`, not code: a list of `{id, packages, decision, requires}` where `packages` are normalised names or a prefix ending in `*`, the first rule that matches wins, `decision` names the entry of `DECISIONS.md` or the row of `docs/VERIFY.md` that pins the package, and `requires` lists the reruns (and `gate`, the full local gate of the runbook) that must be green before the package is taken. A `blocked` entry is information, not a failure: the dry run proposing a newer numpy is normal, and the table says what to run first. The shipped table, a set of unvalidated priors written from the recorded decisions and findings: `eole` and `ctranslate2` (the first entry of `DECISIONS.md`, the `D-EOLE-*` and `D-CT2-*` rows of `VERIFY.md`), the torch family (`torch`, `torch-*`, `torchcodec`, `triton`, `nvidia-*`, `cuda-*`: the cu130 index pin and the decision to keep vLLM out of the workspace), `sacrebleu` and `numpy` (D13: the private statistics API and the goldens), `sentencepiece` (the tokenizer goldens), `transformers`, `tokenizers`, `safetensors` and `sentence-transformers` (the decision about `transformers` 5.21.0), `polars` and `pyarrow` (`D-POLARS-*`), `fastapi`, `starlette`, `uvicorn`, `h11` (`D-SERVE-SIGTERM-EXIT`, `D-UVICORN-LIFESPAN-ORDER`), `huggingface-hub`, `datasets`, `hf-xet` (`D13-HUB-*`) and `pyonmttok`, `fasttext-wheel`, `fasttext-new` (the vendored wheels). **A blind spot, stated in the report and the runbook:** a package pinned with `==` is invisible to the dry run (F13), so these rules fire only for the packages the dry run can see (numpy, polars, pyarrow, starlette, uvicorn, huggingface-hub, the nvidia and cuda wheels, safetensors ...) or after a pin is loosened; whether Eole, CTranslate2, sacrebleu or torch have a newer release is a hand check of the runbook, listed in the monthly pass. Reason: the master plan names the pinned-by-decision packages as the ones an upgrade must not take blindly; data lets the maintainer change the table without a code change, and a test checks every `requires` against the reruns of the same file. Cost if wrong: a wrong table mislabels, never blocks: the cost of a missing rule is a free `drift` row for a package that deserved a gate, and the procedure runs the full gate after every upgrade anyway (M15).

M8. The parity reruns. A rerun is an entry of the configuration `{id, kind, cadence, timeout_seconds, ...}`. `kind: pytest` runs `python -m pytest -q -m "not network" -p no:cacheprovider --junitxml=<out>/junit/<id>.xml <targets>` (targets are files or directories under `tests/`, never a module whose name contains `maintain`: a rerun must not rerun the gate of the command) from the project directory with the interpreter that runs the command (`sys.executable`) and the hidden environment of M10; the outcome is read from the exit code AND the JUnit counters: `ok` only when the exit code is 0, `failures` and `errors` are 0, `passed` (= `tests` - `failures` - `errors` - `skipped`) is at least `min_passed` and `skipped` at most `max_skipped` (default 0); anything else is `fail` with one reason (`pytest exited with code N`, `<f> failed and <e> errors`, `<p> passed, fewer than the floor <m>`, `<k> skipped, more than the allowed <m>`, `timed out after <s> s`, `no JUnit report was written`, `a target does not exist`). A selection that shrank or collected nothing (exit 5) is a failure, never a pass: a golden that was deleted must not turn a rerun green. The counters are the only thing read from the XML (F12). `kind: export_parity` runs `python -m rinchen export parity --checkpoint C --export E --corpus F ... --out-dir <out>/parity_export --max-lines 50 --threads 2 --timeout <t>` and reads the exit code (0 `ok`, 4 `fail` a measured miss, anything else `fail`) and the three numbers of `parity.json` (`exact`, `sentences`, `mean_abs_delta`); it needs `--export`, `--checkpoint` and `--corpus` and is `skipped (no export was given)` without them, whatever the cadence. The shipped reruns (a bound is at least three times the spike's time and at least 300 s: an unvalidated prior for a runner): `numerics` (nightly; the 15 files and `tests/golden` of F7: 1,110 passed; floor 1,100; 300 s), `parity_tiny` (nightly; `tests/integration/test_export_parity.py`: 13 passed; floor 13; 600 s), `parity_export` (nightly cadence, runs only with an export; 600 s), `robustness_tiny` (weekly; D12's gate modules: 31 passed; floor 31; 1,200 s), `evaluation_tiny` (weekly; D13's three gate modules: 99 passed; floor 99; 1,200 s) and `serving_tiny` (weekly; D11's serving gate modules and the engine surfaces: 55 passed; floor 55; 1,000 s). The four pinned things the brief names are covered: Eole against CTranslate2 (`parity_tiny`, `parity_export`), D13's golden report and bootstrap byte for byte and the sacrebleu private API (`numerics`: `test_eval_report_golden.py`, `test_eval_golden.py`, `test_eval_bootstrap*.py`, `test_metrics_segment_stats.py`), D12's floors (`robustness_tiny`: the gate holds them; `numerics` holds the metric goldens). Reason: the existing tests already are the parity checks, with their thresholds as literals that D11 to D13 said are never lowered; the rerun re-asks them under a changed stack and records the answer by name. Robustness is not rerun over an operator's export because D12's command has no threshold (F9). Cost if wrong: a floor that is too low or a selection that drifts shows as a rerun that never fails; `min_passed` is the guard on the second, the gate modules' literals on the first.

M9. The cadence. `--cadence nightly` (the default) selects the reruns whose `cadence` is `nightly`; `--cadence weekly` selects every rerun (a weekly run includes the nightly ones); `--rerun ID` (repeatable) selects exactly those reruns whatever the cadence and wins over `--cadence`; `--no-reruns` selects none. A rerun that exists and is not selected is listed `skipped (not due at the nightly cadence)`. The cadence of each rerun is configuration, not code, and the workflow decides the cadence from the trigger (M14). On this machine the nightly set is about 140 s of reruns (F7, F8) and the weekly set about 1,080 s more (F9 to F11: 388 + 384 + 310), one thread per command (UNMEASURED on a runner). Reason: the cheap, decisive checks every night, the checks that train a toy model once a week; a drift in a golden is caught within a day, a drift in a gate within a week. Cost if wrong: a cadence that is too slow is a number in a file.

M10. The runner seam and the subprocesses. Every process the check starts (`uv`, `pytest`, `rinchen export parity`) goes through `CommandRunner.run(argv, cwd, env, log, timeout) -> CommandResult(exit_code, timed_out)`; the library takes the runner as an argument, the command builds `SubprocessRunner`, and every test of the library uses a recording fake with recorded outputs, so no test needs `uv`, a network or a model. `SubprocessRunner` starts the process with `shell=False`, standard input closed, standard output and error combined into the log file, in its own session, and on a timeout kills the whole process group and reaps it (`rinchen.utils.logged_process.run_logged` does the same but raises on a non-zero exit and so hides the code a pytest rerun needs, F16). The environment of a child is a copy of the parent's with `CUDA_VISIBLE_DEVICES=""`, `HF_HUB_OFFLINE=1`, `HF_DATASETS_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1` set, and for `uv` also `NO_COLOR=1`, `UV_NO_PROGRESS=1`, `UV_PYTHON_DOWNLOADS=never`; nothing of the environment is ever written to a report, a log line or a manifest. Every process has a timeout from the configuration; `auto` is not a value of anything here. Cost if wrong: an unbounded child would hold a job for its whole limit; the runner test kills a grandchild through a real process group.

M11. The report. `maintain_report.json`, schema `rinchen.maintain/1`, UTF-8, sorted keys, two-space indent, one final LF, built only from observations: `{schema, cadence, state, inputs: {config, lock, pyproject} (SHA-256), lock: {packages, names, format: {version, revision}}, steps: [{id, state, reason, detail}]}`; `detail` is `{checks: [{id, state, reason}]}` for the doctor, `{installed, mismatched: [{name, installed, locked}], extra: [name], not_installed, ...}` for the environment, `{entries: [...], counts: {update, add, remove, drift, blocked}, warnings}` for the drift step and `{items: [{id, kind, cadence, state, reason, tests: {passed, failed, errors, skipped} or null, figures: {...} or null}]}` for the reruns. No timestamp (only the manifest has `created`), no absolute path, no environment value, no secret, no line of any program's output, no host name; a name is a package name or an id that matched its pattern, a version is a string from the lock or from uv after the cross-check; every message names ids and counts. The same observations give the same bytes. `maintain_report.md` is rendered from the report alone (a header with the state and the cadence, a table of checks, the drift table (at most 200 rows and a line saying how many more are in the JSON), the rerun table, a short "what to do" line per failing step pointing at a section of the runbook, and the fixed sentence of the blind spot of M7); it is what the workflow copies to the run page. Reason: D13's report rules (recomputable, no timestamp, no path) carried over; a report that cannot be diffed night to night is not a record. Cost if wrong: a path in the report would leak a home directory into a run page; the gate scans both files for paths, timestamps and the environment.

M12. The output directory and the manifest. `--out-dir` receives `maintain_report.json`, `maintain_report.md`, `logs/` (the output of uv and of each rerun: local files that can hold paths and are never uploaded), `junit/` (the counters' source) and, LAST, `manifest.json` (stage `maintain_check`). The commit order is D13's: the old manifest is removed before anything else is touched (`begin_commit`), a manifest of another stage in the directory is refused (exit 3, nothing removed), the files the old manifest listed are removed by name from inside the directory, the outputs are written whole or not at all (`replace_file`), the manifest is written when everything it lists exists. The manifest holds: `inputs` (`pyproject.toml`, `uv.lock`, the configuration, each with the SHA-256 taken before it was read), `outputs` (every file written with its digest), `config_sha256` (the configuration's), `seed -1`, `tool_versions` (EVERY name of the lock with its locked version, a name with several versions joined by `, ` in sorted order, plus `python` and `uv`; the versions come from the lock, i.e. the resolved set, and equal the installed ones when the environment step is `ok`), `metrics` (counts: packages, entries of the table, blocked, reruns run, and the seconds of each step) and `status` (each step's state). Hash before read: the three inputs are hashed first and parsed from the bytes hashed (`verified_content`); one that changed in between is exit 2. The output directory must not be the project directory or the directory of an input. Reason: CLAUDE.md requires every resolved package version and the lock's hash in manifests, and D13's commit protocol is the project's; the manifest, not `docs/STACK.md`, is the machine-readable record. Cost if wrong: a manifest that vouches for a half-written run makes a nightly look complete; the order is tested by interrupting between writes.

M13. The inputs. `--project-dir` (default: the repository root) holds `pyproject.toml`, `uv.lock` and the tests the reruns select; `--config` defaults to `configs/maintain/maintain.yaml`; the configuration is a closed document (pydantic `extra="forbid"`, every key required, no environment is read) parsed from the bytes hashed. Targets are relative paths under `tests/` without `..`; timeouts are integers from 1 to 14,400; ids match `[a-z][a-z0-9_]{0,31}` and rule ids `[a-z0-9-]{1,40}`; a rerun id that repeats, a `requires` that names no rerun (the word `gate` is allowed), a `cadence` other than `nightly` or `weekly` and a `kind` with the fields of the other kind are refused naming the field. `requires-python` and the exact pins of `pyproject.toml` are not interpreted: the check reads the lock, not the project metadata.

M14. The nightly workflow. `.github/workflows/nightly.yml`: triggers `schedule` (`17 3 * * *` every night and `47 4 * * 0` on Sunday) and `workflow_dispatch` with a `cadence` choice input; `permissions: contents: read`; one job `maintain` on `ubuntu-24.04` with `timeout-minutes` above the sum of the weekly bounds and the fixed overhead (a test computes it from the configuration); the cadence in an `env` expression (the dispatch input, else `weekly` for the Sunday cron, else `nightly`); steps: checkout, `setup-uv`, `setup-python` 3.14, `setup-just` (the same actions at the same versions as `ci.yml`, a test checks), `uv sync --frozen --group dev`, `uv run rinchen maintain check --out-dir maintain-out --cadence "$CADENCE"`, `just tiny` (the stub until D15, then the real pipeline: the nightly job picks D15 up without an edit), and, `if: always()` and only when the file exists, `cat maintain-out/maintain_report.md >> "$GITHUB_STEP_SUMMARY"`. Caching policy: whatever `setup-uv` does by default; no step caches a virtual environment, a Hugging Face directory or a model; no key is built from a secret; nothing persists from one run to the next that a run wrote. Failure notification: the job fails (exit 4 of the command), which is GitHub's own notification; nothing needs a secret. **What it never does:** use a secret or an `env` of a secret; upload (no `upload-artifact`, no `--upload`); push, commit, open or merge a pull request (`git push`, `git commit`, `gh `); run `uv lock`, `uv add`, `uv pip`, `uv sync` without `--frozen` or any `--upgrade` (the dry run happens only inside the command, whose loader refuses a configuration without `--dry-run`); mention docker, a GPU runner, CUDA, nvidia or a self-hosted runner; print the environment (`printenv`, `env |`, `set -x`, `echo $`). A static test (`tests/unit/test_nightly_workflow.py`, PyYAML; the trigger is under the key `True`) checks each, and runs the scan over broken copies of the file. The workflow is NEVER run here (UNMEASURED); what is measured is that its command runs green natively (the gate, M19). Reason: the master plan's D0 asks for the nightly run of the tiny pipeline and D14's asks for the check; one job keeps one report. Cost if wrong: a wrong expression would run the weekly set every night (a cost, not a failure) or never; the static test pins the two cron strings to the two cadences.

M15. The upgrade procedure and the rollback (the runbook has the commands; this is the contract). Upgrade: on a branch, never on `main`; read the table of the last report and pick one package or one family (`uv lock --upgrade-package NAME`, never `--upgrade` for everything); `uv sync --group dev`; `just gate`; `rinchen maintain check --cadence weekly --no-drift` (and `--export ... --checkpoint ... --corpus ...` for a real export) and every rerun that the package's rule `requires` must be `ok`; a golden that moved is either a regression (revert) or an intended change recorded in `DECISIONS.md` with the new golden and the reason, in the same commit; record the upgrade in `DECISIONS.md` (package, versions, rule, reruns, date) and refresh the hand snapshot `docs/STACK.md` (`uv pip list`); merge by the usual review. Rollback: `git revert` of the commit that moved `uv.lock` (or `git checkout <good> -- uv.lock pyproject.toml`), `uv sync --frozen --group dev`, `rinchen maintain check --no-drift` until the environment, the lock check and the parity reruns are `ok`, and a line in `DECISIONS.md`. The procedure never edits a pin of the packages of M7 without a decision: loosening an exact pin is a decision, not a maintenance step. Cost if wrong: an upgrade taken on `main` without the reruns; the runbook names the order and the check that proves it.

M16. What each failure means (the runbook's table, one row per id): a doctor `fail` is a broken install (`uv sync --frozen --group dev`; `docs/VERIFY.md` for the check); `lock_file` exit 3 is a lock this version of rinchen cannot read; `lock_consistent` `fail` is a `pyproject.toml` that moved without `uv lock` (lock on a branch, run the gate); `environment` `fail` is a machine that is not the lock (`uv sync --frozen --group dev`) or a stray package; `drift` `fail` is uv failing, timing out or printing what the parser does not know (read `logs/drift.log`; a new format is a fixture and a regular expression); a `drift` table is the normal state; a `blocked` row names the reruns to run before taking it; a `numerics` `fail` means a library, the Python patch release or the runner's C library moved a number a golden pins (revert or record); a `parity_tiny` or `parity_export` `fail` means Eole, CTranslate2 or torch moved the greedy output or the log-probabilities (do not upgrade; read the mismatch list of `parity.json`); the weekly reruns fail for the same reasons one layer up.

M17. What D15 takes. (1) The state vocabulary (`ok`, `skipped` with a reason, `fail`) and the way a step lists its reason: the tiny pipeline's `report.json` can carry its stages the same way. (2) A quick preflight: `rinchen maintain check --no-drift --no-reruns --out-dir DIR` is the doctor, the lock check and the environment check in about 15 s (F1, F4, F5), with nothing the network or a model needs. (3) The parity of D15's own tiny export: `--rerun parity_export --export DIR --checkpoint DIR --corpus FILE` runs D11's command and records it by name; D15 may also call `rinchen export parity` itself, which it can already do. (4) The nightly job already runs `just tiny`, so D15's real pipeline is picked up by the schedule without a workflow edit. Nothing in D14 blocks D15, and D15 needs nothing of D14.

M18. Layering and hygiene. `rinchen.maintain` and `rinchen.config.maintain` import only the standard library, pydantic, PyYAML, `rinchen.errors` and each other (an AST scan over every module of the package, `tests/unit/test_maintain_layering.py`); the command modules (`cli/maintain*.py`) may import `rinchen.cli.doctor`, `rinchen.cli.errors`, `rinchen.cli.train_common`, `rinchen.export.verified`, `rinchen.manifest` and `rinchen.maintain`, never `train`, `serve`, `eval`, `synth`, `infer`, `annotate`, `filter`, `ctranslate2`, `eole`, `torch`, `sentencepiece`, `polars` or `huggingface_hub`; nothing but `cli/main.py` imports `cli.maintain`. No new dependency (`pyproject.toml` and `uv.lock` are not edited). No file over 450 lines. No timestamp in the report or the Markdown. No GPU question anywhere (an AST scan as D11's and D12's: `torch.cuda`, `get_cuda_device_count`, `nvidia-smi`). No network in any test: every unit test of the library uses the fake runner and every test module that could reach a socket runs under the `no_network` fixture. No message, log line or report holds a line of another program's output. Nothing the project's content rules in CLAUDE.md exclude appears in any file D14 adds (a scan of every D14 document and test, as D13's). Every subprocess of a test is bounded.

M19. Tests, doubles and the gate. Section 5.

## 5. Tests and the gate

- Unit tests per module with KNOWN answers: the loader's every refusal (naming the field), the shipped table's invariants (the ids, the targets exist, every `requires` is a rerun or `gate`, the doctor's partition); the lock reader over a committed sample lock (duplicate names, a local version label, the editable project, every refusal) and over the real `uv.lock` for invariants only (the entry count equals a regular expression's count: never a literal, so the first upgrade does not break a test); the environment comparison; the dry-run parser over the MEASURED no-change and failure outputs and the HAND-WRITTEN change output (both spellings of each verb, ANSI, CRLF, local version labels, a contradiction, an unknown line, an empty output), with a property test that no text without the positive line or a change line can be `ok`; the drift table's classification and cross-check; the runner over real subprocesses (exit code, timeout with a grandchild killed, the environment, the log); the JUnit reader and the rerun outcomes over a scratch project run by the real pytest (the four outcomes of F12); the report and the Markdown against golden files, determinism, the content scans (no path, no timestamp, no environment value); the command over fakes (every option, every exit code, nothing written when an input is refused, hash before read, the manifest last, the foreign manifest, equal bytes on a rerun); the workflow's static checks over the file and over broken copies; layering, GPU and message scans.
- The gate (`tests/integration/test_maintain_gate.py` and `test_maintain_gate_controls.py`, real binaries, CPU, GPU hidden, every subprocess bounded): the command of the workflow's maintain step, read from `nightly.yml` and run with a shell with `CADENCE=nightly`, through a shim named `uv` first on `PATH` that (a) answers `lock --upgrade --dry-run` with the HAND-WRITTEN sample and never forwards it, (b) forwards `lock --check` to the real uv with `--offline` added, `--version` and `run` (as `run --project <repository> --no-sync --frozen --offline`, F18) and (c) refuses any other argument and every `--upgrade` that is not that dry run; and the real reruns on the toy. R1 to R9 are in the plan (Task 7). A miss of a floor is answered with more steps of the toy, never a lower floor.

## 6. Open questions, recorded as such

1. The lines `uv lock --upgrade --dry-run` prints for an update, an add and a remove, and its exit code when it finds changes: UNMEASURED (F3). The design refuses what it does not know; the first online run must be turned into a recorded fixture and an amendment.
2. GitHub Actions: that the workflow starts, that `github.event.schedule` holds the cron that fired, that `hashFiles` and `env.CADENCE` work in a condition, the runner's speed and core count (the bounds are three times a 20-core machine's single-thread times), the minutes budget of a private repository (a nightly of about 10 minutes and a weekly of about an hour, ARITHMETIC) and the setup actions' own caching: all UNMEASURED.
3. The real state of PyPI: what the drift table holds on a given night, and whether a package pinned with `==` has a newer release (invisible to the dry run, F13). `uv tree --outdated` could show it; its output is unmeasured and is not built.
4. Everything GPU: no rerun, doctor check or step touches a device; a CUDA wheel upgrade (`nvidia-*`) cannot be qualified here.
5. Real data and real exports: the reruns run on the toy, which ranks nothing; `parity_export` is exercised only on the D11 toy export; a robustness or evaluation rerun over a real export needs floors nobody has set.
6. The shipped rule table and the bounds are priors written from the recorded decisions and one machine's times.
7. The nightly job and the weekly job cost minutes and cannot be tested for flakiness here; a flaky weekly rerun (the toy trains from a seed, so it should not be) would need a retry policy, deliberately not built.
8. `docs/STACK.md` is a hand snapshot; a script that regenerates it from the manifest is the obvious next step.
9. D15 decides whether `just tiny` calls `maintain check --no-drift --no-reruns` as a stage.
