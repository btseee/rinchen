# D7 Multilingual ablations: design

Status: binding for the D7 plan (`docs/superpowers/plans/2026-11-08-d7-multilingual-ablations.md`) when it was written, and AMENDED to the finished code in Task 9 (every contract below is the code as of the last commit of the branch; section 8 lists each ruling and decision made while building). Master plan: `docs/research/2026-10-29-rinchen-dev-agent-prompt.md`, milestone D7. Evidence for every Eole fact below: `.superpowers/sdd/2026-11-08-d7-multilingual-ablations/spike-findings.md` (a spike on this machine, Eole 0.6.4, CPU, toy templated data) and `docs/VERIFY.md` (section "D7 findings"). Operator guide: `docs/runbooks/07_ablations.md`.

## 1. Goal and non-goals

Goal: `rinchen train ablate --matrix X` expands an ablation matrix (temperature sampling of the directions, the ratio of back-translated data, the placement of the direction tag, and seeds) into N variants; for each variant it builds the training mixture, renders a schema-validated Eole config, trains a model from random init, translates the development set of every direction, scores it, and writes a results table. STOP gate: a tiny ablation of 2 variants trains and evaluates through the real CLI on CPU (met: 72.7 s, dev chrF 96.25 to 99.72 in every direction of both variants).

Non-goals (stated so nobody assumes them):
- No real data exists, and no GPU was used: every number the gate measures is a toy number on templated sentences that saturate at chrF 96 to 100 and cannot rank variants. The ablation machinery is tested; the ablation CONCLUSIONS (which temperature, which bt ratio, which placement) are not produced by D7 and need real corpora and GPU hours.
- No teacher training (D8), no averaging, no CTranslate2 export or serving (D11), no robustness or final evaluation suites (D12, D13), no document-level data (D9), no distillation (D10).
- Evaluation uses the DEV split only (model selection). The test split and FLORES+ devtest are never read here.
- No fine-tuning, LoRA or continued training: every variant is trained from random init (`train_from` is not an allowed Eole key).

## 2. Findings that bind the design

1. Eole 0.6.4 rejects unknown keys at every level of `eole train` (`extra_forbidden`), but `eole build_vocab` ignores some: our own validation must catch typos before either runs (`D-EOLE-UNKNOWN-KEYS`).
2. `data.<corpus>.weight` is an integer: the number of consecutive examples taken from that corpus per round of a cyclic round robin. Proportion is exactly `w_i / sum(w)`, independent of corpus size; an exhausted corpus restarts. Temperature sampling therefore needs integer weights (`D-EOLE-WEIGHT-SEMANTICS`).
3. Eole's own `sentencepiece` + `prefix` transforms work for training with several corpora per direction and a per-corpus `src_prefix` of several pieces (`<2khk_Cyrl> <bt>` splits on the space into two pieces). Both `src_prefix` and `tgt_prefix` must be present on every corpus that uses `prefix` (a missing one is a `TypeError` at `build_vocab`); `''` means none.
4. Eole 0.6.4 takes ONE validation corpus, named `valid`; it copies that corpus's prefix into the saved checkpoint and lets the checkpoint override the prediction config (`D-EOLE-PREFIX-OVERRIDE`, D5). A validation corpus that carries no prefix keys and is PRE-TOKENISED by the harness (`transforms: []`, the direction tag as a single piece) works for every placement and leaks nothing into the checkpoint.
5. Prediction is done as D5 does it: the harness pre-tokenises with the SentencePiece model, `transforms: []`, greedy decoding, one output line per source line.
6. Tag on the SOURCE (`src_prefix`) works with no forcing and is comparable across variants. Tag on the TARGET (`tgt_prefix`) trains, but prediction needs the tag forced: a `tgt` file with the tag per line plus `tgt_file_prefix: true`; Eole's output then STARTS with the forced tag (strip it), and without forcing an ambiguous direction fails (mn2ru chrF 16). Hazard: Eole drops an example whose tokenised source equals one already in the same minibatch (`D-EOLE-BATCH-DEDUP`); with the tag on the target, multi-parallel data (the same source in several directions) loses 1.9% of the examples at 1024-token batches, 35.6% at 4096 and 50% at 16384, silently. With the tag on the source, 0.00%.
7. A source-suffix tag needs Eole's separate `suffix` transform and trips an Eole bug (`SuffixTransform.get_specials` raises `KeyError: ''`, `D-EOLE-SUFFIX-KEYERROR`) unless a workaround corpus is configured: NOT supported in D7 (documented as a finding).
8. Same seed AND same thread count give byte-identical checkpoints and predictions; different thread counts do not. Threads are pinned (default 2) and recorded.
9. SentencePiece: the project's `train_spm` cannot build a vocabulary below about 458 pieces (118 reserved symbols + 256 byte pieces + characters); the toy run uses 640 (the spike used 673, the largest the text supports).
10. Eole loads a checkpoint through `glob(<model_path>/model.*.safetensors)`, so `[`, `]`, `*` and `?` in the checkpoint directory make it find no shard or a sibling's shards (`D-EOLE-GLOB-CKPT`, found in review).
11. Once polars is imported, a blocking untimed wait on the main thread is not interrupted by SIGINT (`D-POLARS-SIGINT`), and a SIGTERM or SIGHUP to `rinchen` leaves a session-isolated `eole` child running (`D-LOGGED-TERM`): `run_logged` polls its wait and turns both signals into an exit.

## 3. Rulings

R1. Placements are `src` (default) and `tgt`. `suffix` is out (finding 7): `tag_placement: [suffix]` is a `ConfigError` that names the bug.
R2. Corpora are `(direction, group)` pairs, `direction = f"{src_lang}-{tgt_lang}"`, corpus name `f"{direction}.{group}"`. Groups: `auth` (origins human, web, mined, converted) and `bt` (origin bt). Only rows with `split == "train"` are training rows; each other row is counted once, under the first reason that applies, in this order: `not_train`, `filtered` (a `filter_reason` is set), `excluded_origin` (origins ft, synth_llm, synth_nmt are NOT used in D7, forward-translated data enters training with D8/D10; also counted by origin), `empty` (null, empty or whitespace-only text), `line_break` (a character `str.splitlines` splits at). The invariant `rows_read = rows_kept + the exclusions` holds. Dev rows go through `filtered`, `empty` and `line_break` and are counted apart.
R3. Temperature follows `rinchen.utils.sampling.temperature_weights` (D3): `p ~ size ** T`, T below 1 lifts small corpora, 1 is proportional. It acts on DIRECTIONS (total rows of the direction, auth + the bt rows used); inside a direction the corpora share its probability in proportion to their rows. So `bt_ratio` fixes the bt share of a direction (`r / (1 + r)` when enough bt rows exist) and `temperature` fixes the balance between directions.
R4. `bt_ratio` r: per direction the bt corpus gets `min(available, round(r * n_auth))` rows (Python `round`: a half goes to the even integer), chosen by a seeded hash rank (`sha256(f"{seed}\t{id}")`, smallest first, ties by id, source, target), independent of the input order and of the polars version; `r = 0` or no authentic rows in the direction means no bt corpus (a direction with bt rows and no authentic rows trains nothing, and no authentic row at all is a `DataError`); a shortfall is not an error, it is recorded (`bt_available`, `bt_requested`, `bt_used`).
R5. Integer weights: every corpus gets at least 1; the weights sum to `weight_total` (default 100, at least the number of corpora, else a `ConfigError` that names the number needed); largest-remainder rounding with ties by corpus name (never by input order); a larger probability never gets a smaller weight. The upsampling of each corpus per variant is computed and recorded: `(w_c / sum of the weights) / (rows_c / sum of the rows)`, so 1.0 means the corpus is drawn as if every row of the mixture were drawn alike and more than 1 means its rows are seen more often (an epoch count would need the batch composition, which Eole decides; the first draft said "effective epochs").
R6. The training corpora are plain text files (one sentence per line, LF only, no tags): the tags are Eole `prefix` configuration, so placement is a config difference, not a data difference. Authentic corpora are built once (`data/auth/`) and shared by every variant; bt subsamples once per distinct ratio and seed (`data/bt/r<ratio>_s<seed>/`). A corpus is reused when its `<name>.json` sidecar (row count and SHA-256 of both files) equals what would be written and the files on disk have those digests.
R7. The validation corpus and the development evaluation use the dev rows (`split == "dev"`, null `filter_reason`, usable; at most `dev_max_lines` per direction, by id, then source, then target). The harness writes the validation corpus pre-tokenised (finding 4): the source tokens `[tag] + pieces` for `src`, `pieces` for `tgt`; the target tokens `pieces` for `src`, `[tag] + pieces` for `tgt`.
R8. A variant's evaluation is ONE `eole predict` call (greedy, CPU) over the concatenated dev sources of all directions (the model loads once), split back by direction; scores are corpus chrF and corpus BLEU (sacrebleu defaults, signatures recorded) per direction, the macro mean and the minimum of chrF over directions, and `tag_leaks` (hypotheses that contain the direction tag of any registry language or `<bt>`).
R9. `source_collision_rate`: the share of kept training rows whose source text occurs in at least one other kept row of a different target language. It is recorded for every variant (one number for the run, before any bt subsample), printed in the dry run and in the tables, and explained in the runbook as the exposure to finding 6's hazard; it is informational, not a gate.
R10. Resume: a variant is complete when its `result.json` parses (strictly), says `ok`, its `fingerprint` equals the current one, it scores exactly the plan's dev sets line for line, and its checkpoint file has the recorded SHA-256 (the fingerprint holds the rendered config text, the hashes of its corpus files and validation files, of the raw dev texts and of the SentencePiece model, the thread count, the versions of Eole, torch, SentencePiece and sacrebleu, and the tag placement). A complete variant is reused, `--force` redoes everything. Right after a training, before the evaluation starts, `train.json` records the fingerprint, the checkpoint's SHA-256 and the training seconds; a variant that is not complete but whose `train.json` parses (strictly), holds the current fingerprint and whose checkpoint file has the recorded SHA-256 is only evaluated again, so a failed or interrupted evaluation does not discard a trained checkpoint (any other `train.json` is ignored and removed before a retraining; `train.json` stays after a success). A variant that fails stops the run with the cause; completed variants stay.
R11. Every Eole config rendered by D7 passes `validate_train_config`: curated allow-lists of keys (each checked against the installed Eole's fields by a test), the forbidden-key list (relative, rotary, ALiBi, sliding window, grouped-query attention; moved from D5), `model.architecture: transformer`, `SinusoidalInterleaved` explicit, only plain YAML data, no `$` anywhere (Eole expands environment variables in the YAML text), `overwrite: true`, `share_vocab: true`, no `train_from`. The plan validates the config of every variant in memory (so a dry run catches a typo) and the preparation validates it again when it renders.
R12. The shared Eole machinery D5 built moves out of `script_conv` into neutral homes (`rinchen.utils.logged_process`, `rinchen.train.eole_cfg`, `rinchen.train.eole_run`); D5 imports it from there. D5's behaviour, error wording and tests do not change, with two exceptions that are recorded in section 8 (the polled wait of `run_logged`, which changed four D5 test assertions, and the refusal of glob characters in a checkpoint directory, which makes D5 fail earlier).

## 5. Contracts

### 5.1 `rinchen.train.eole_cfg`

- `FORBIDDEN_KEYS: frozenset[str]` (D5's 16 names, moved; D5 re-exports it), `POSITION_ENCODING = "SinusoidalInterleaved"`.
- Allow-lists (frozensets, one per level; the exact members are in the module and in `docs/runbooks/07_ablations.md`): `TOP_LEVEL_KEYS` (15), `CORPUS_KEYS` (6: path_src, path_tgt, transforms, weight, src_prefix, tgt_prefix), `TRANSFORMS_CONFIGS_KEYS` (2: sentencepiece, filtertoolong), `SENTENCEPIECE_KEYS` (2), `FILTERTOOLONG_KEYS` (2), `MODEL_KEYS` (9), `ENCODER_KEYS` and `DECODER_KEYS` (5 each), `EMBEDDINGS_KEYS` (2), `TRAINING_KEYS` (27; `accum_steps` is not among them). The rule: only keys a D7 run uses or an operator plausibly overrides in an ablation, each present in the installed Eole's pydantic models (a test imports `eole.config` and checks every allowed key at its level against the model fields; a second test checks every forbidden key is still a real Eole field, as D5 does).
- `validate_train_config(cfg: object) -> None`: raises `ConfigError` whose message is `invalid Eole config: <dotted.path>: <problem>`, for the first rule broken in this order: (1) not a mapping; (2) a forbidden key at any depth; (3) a `$` in any key or string; (4) a value that is not plain YAML data of exactly its type (a subclass such as an enum member is refused) or a mapping or list that contains itself; (5) a section that is not a mapping, or an unknown key at any level (the message names the key and the level; a corpus name must be text); (6) `model.architecture` other than `transformer`; (7) `model.embeddings` missing, or its `position_encoding_type` (and any encoder/decoder one present) not exactly `SinusoidalInterleaved`; (8) `model.hidden_size` or `model.embeddings.word_vec_size` missing or different (Eole's default 512 breaks a smaller model), or an encoder/decoder `hidden_size` that differs; (9) `overwrite` or `share_vocab` not `true`; (10) a corpus other than `valid` without `path_src`, `path_tgt` (non-empty text), `transforms` (a list of strings), `src_prefix` or `tgt_prefix` (strings; finding 3), or with a `weight` that is not a positive integer; `data.valid` with a `transforms` entry other than an empty list, with prefix keys or with a `weight` (finding 4). It does not check the type of the value of a known key (Eole's pydantic does at `eole train`).
- `merge(base: Mapping, overrides: Mapping) -> dict`: deep merge; mappings merge, everything else replaces; an override value of `None` deletes the key (also inside a mapping that replaces a value, so merging the same overrides again changes nothing); neither input is modified.
- `merged_config(base: Path, overrides: Mapping) -> dict`: reads `base` (`ConfigError` for a missing, unreadable, unparseable, empty or non-mapping file, a `$` in its text or a recursive anchor), refuses self-containing overrides, merges and validates; writes nothing. The base need not be complete before the merge.
- `render(base: Path, overrides: Mapping[str, Any], out: Path) -> Path`: `merged_config` then writes `out` (parents created, atomically through `utils.part_file`); `ConfigError` for an `out` that is the base (once links are resolved), a directory, or below a non-directory; a failing config writes nothing.
- `read_config(path: Path, what: str) -> Any` (whatever the YAML holds: D5's validators own the shape check and its wording, so `render` and `validate_train_config` check for a mapping themselves; `ConfigError` for a missing, unreadable or unparseable file, a `$` in the text or a recursive anchor), `dump_config(cfg, path)` (atomic; `ConfigError` when YAML cannot dump a value), `reject_dollar(what, value)` and `reject_glob_characters(what, value)` (a `ConfigError` naming the path and the character for `[`, `]`, `*`, `?`; finding 10).

### 5.2 `rinchen.train.eole_run` and `rinchen.utils.logged_process`

- `training_environment(threads, *, hide_gpu) -> dict[str, str]`: a copy of the environment with `OMP_NUM_THREADS` and `MKL_NUM_THREADS` set and, when `hide_gpu`, `CUDA_VISIBLE_DEVICES=""`; `ValueError` below one thread.
- `run_training(cfg_path, run_dir, *, validate, threads=2, timeout=None, what="Eole config") -> Path`: the D5 flow made generic: `$` rejected in the path and the run directory, `validate(cfg)` (a callable that raises `ConfigError`), `training.model_path` inside `run_dir` and free of glob characters, `eole build_vocab -n_sample -1` then `eole train` (the GPU hidden when `training.gpu_ranks` is empty), a fresh `model.00.safetensors` required; returns the checkpoint directory. D5's `run_training` is a wrapper that passes its converter validator.
- `predict_tokens(ckpt_dir, source_tokens, *, out_dir, forced_prefix_tokens=None, threads=2, timeout=None, batch_size=64, stem="eole", stale_files=()) -> list[str]`: writes the token lines under `out_dir` (`predict_files(out_dir, stem)`), runs `eole predict` greedily on the CPU with `transforms: []` (and `tgt` + `tgt_file_prefix: true` when `forced_prefix_tokens` is given), returns Eole's output token lines, exactly one per source line. `ValueError` for fewer than one thread, no source line, a number of forced prefixes different from the number of source lines, or an empty or whitespace-only forced prefix or source line when prefixes are forced (Eole drops such an example silently); `ConfigError` for `$` in the checkpoint directory, output directory or stem and for a glob character in the checkpoint directory; `UpstreamError` for a non-zero exit, a timeout, a missing `eole`, a missing output or another line count. `stale_files` are removed once every check has passed and before Eole runs.
- `run_logged(command, *, env, log_path, what, timeout=None) -> None`: output into `log_path`, no stdin, the child leads a session of its own; the wait is made in slices of 0.2 s that never run past a monotonic deadline (so Ctrl-C is raised promptly, finding 11); while it waits on the main thread SIGTERM and SIGHUP raise `SystemExit(128 + signal)` and the handlers are restored afterwards; on a timeout, an interrupt or such a signal the child's process group is killed and reaped. A non-zero exit or a timeout is an `UpstreamError` that names `what`, the log and its last 20 lines.

### 5.3 `rinchen.train.sampling`

- `CorpusSize(name, direction, rows)` (frozen).
- `mixing_probabilities(corpora: Sequence[CorpusSize], temperature: float) -> dict[str, float]`: R3. Positive, sums to 1, keyed in the order given, independent of that order. `ValueError` for no corpus, a repeated name, a corpus without rows (the caller drops it first), a temperature that is not positive and finite, and a temperature so large that the sizes raised to it do not fit a float.
- `integer_weights(probabilities: Mapping[str, float], *, total: int = 100) -> dict[str, int]`: R5. `ValueError` for no probability, a probability that is not positive and finite or a sum that is not 1 within 1e-9; `ConfigError` for more corpora than `total`.

### 5.4 `rinchen.metrics.bleu_chrf.corpus_scores`

`corpus_scores(hypotheses: Sequence[str], references: Sequence[str]) -> CorpusScores`, `CorpusScores(chrf: float, bleu: float, chrf_signature: str, bleu_signature: str)`; `ValueError` for different lengths or empty input; both scores clamped at 100.0 (sacrebleu reports 100.00000000000004 for identical text); a fresh metric per call, because a signature is known only after scoring; all-empty references score 0.0. Sentence-level `chrf` stays as it is.

### 5.5 `rinchen.config.ablation` and `rinchen.train.variants`

```yaml
name: tiny
base: configs/eole/multilingual_tiny.yaml   # relative paths are repo-anchored like the other configs
axes:
  temperature: [0.5]          # each > 0 and finite, distinct as printed; default [1.0]
  bt_ratio: [0.5]             # each >= 0 and finite, -0.0 refused; default [0.0]
  tag_placement: [src, tgt]   # src | tgt; "suffix" is refused by name; default [src]
seeds: [1234]                 # distinct non-negative ints; default [1234]
weight_total: 100
dev_max_lines: 1000
max_variants: 64              # a guard: expansion above it is a ConfigError at load
overrides: {}                 # merged into every variant's Eole config, last; None deletes a key
```

`AblationMatrix` and `Axes` (pydantic, `extra="forbid"`, frozen, strict types: a quoted number or a YAML boolean is an error, and the text `1e-5` that PyYAML reads gets a message asking for `1.0e-5`), `load_ablation(path)` (`ConfigError` like `load_synth_config`). `TagPlacement = Literal["src", "tgt"]`, `require_placement` (ValueError), `id_number(value)` (`f"{value:g}"`, shared by the id, the corpus directory of a bt subsample and the tables). Duplicates are detected as printed. `Variant(id, temperature, bt_ratio, tag_placement, seed)` frozen; `expand_variants(matrix)` returns the product in the order temperature, bt_ratio, tag_placement, seed (the seed fastest); the id is `t{T:g}_bt{r:g}_{placement}_s{seed}`; the count is checked against `max_variants` when the matrix is built.

### 5.6 The mixture: `mixture`, `corpus_files`, `eole_data`, `validation_corpus`

- `mixture.load_training_rows(paths: Sequence[Path]) -> TrainingRows(frame, stats, directions)` and `load_dev_rows(paths, *, max_lines, directions, training=None) -> DevRows(sets, stats)` read the corpus Parquet files (`scan_corpus`, `glob=False` paths; the split filter is part of the lazy plan, so the text of other rows is not decoded), apply R2 and R7. `MixtureStats` (JSON-ready): `rows_read`, `rows_kept`, `excluded` (every reason, 0 where none), `excluded_by_origin`, `duplicate_ids` (duplicates are kept and counted), `rows_by_corpus`, `source_collision_rate`. `DevStats`: `rows_read`, `rows_usable`, `excluded`, `ignored_by_direction`, `available_by_direction`, `lines_by_direction`, `dev_in_train` (the returned lines whose id is that of a kept training row; None without `training`). `directions` are those with authentic rows. `DevSet(direction, src_lang, tgt_lang, ids, src, tgt)`.
- `corpus_files.build_corpora(rows, *, bt_ratio, seed, data_dir) -> BuiltCorpora(corpora, bt_by_direction)`: writes `<name>.src`, `<name>.tgt` (LF only; UTF-8; rows sorted by id, source, target) and the sidecar `<name>.json` for the `auth` and, per R4, the `bt` corpora; reuse per R6. `planned_corpus_sizes(rows, bt_ratio)`, `planned_corpus_files(rows, bt_ratio, seed, data_dir)` and `bt_usage_by_direction(rows, bt_ratio)` decide the same corpora without writing, and the build is made from them, so a plan cannot disagree with a build.
- `eole_data.data_section(corpora, weights, placement, *, valid_paths, filtertoolong) -> dict`: the Eole `data` section (transforms `[sentencepiece, prefix]` plus `filtertoolong` when the finished config configures it; prefixes per placement; `<bt>` after the direction tag in `src_prefix` for `src` and alone in `src_prefix` for `tgt`; the `valid` entry with two paths and nothing else per finding 4). `ValueError` for a bad placement, no corpus, repeated names, a missing weight or a weight for no corpus; `ConfigError` for `$` in a path. Tags come from `config.languages.direction_tag` and `synth.tags.data_origin_tag`.
- `validation_corpus.write_validation(dev, spm_model, placement, out_dir) -> ValidPaths(src, tgt)`: R7; `dev_token_lines` is the one function that also feeds the evaluation. `ConfigError` when the SentencePiece model cannot be loaded or a direction tag is not one piece.
- Errors: `ConfigError` for a language outside the registry (among the rows that would train); `DataError` for an unreadable corpus file (a Parquet reader panic included), a file that is not a corpus table, a null id, language or origin in a row that would be used, no training rows, no authentic rows, or a dev set that is empty for a direction that has training rows.

### 5.7 `rinchen.train.evaluate`

`evaluate_variant(ckpt_dir, dev, *, spm_model, placement, out_dir, threads=2, timeout=None, predict=predict_tokens) -> DevResult` per R8 (`predict` is the test seam, with the signature of `predict_tokens`; it is called with `stem="dev"` and the hypothesis files as `stale_files`). The token lines, the per-direction line ranges and, for `tgt`, the forced prefixes come from `validation_corpus.dev_token_lines`. It strips the forced first token for `tgt` (a first token that is not the forced tag is an `UpstreamError` naming the direction and the line, never the text), decodes with SentencePiece (`line.split(" ")`, never `str.split()`; a line feed in a hypothesis becomes a space), writes `hyp.<direction>.txt` beside Eole's own `dev.*` files in `out_dir` after everything else has succeeded, and never reads anything but dev rows. `DevResult(directions, chrf_mean, chrf_min, tag_leaks, chrf_signature, bleu_signature)` holds per direction `DirectionScores(lines, chrf, bleu)`; `to_dict()` gives the raw, unrounded values. `ValueError` for a bad placement or a direction name with `/`, `\` or NUL; `DataError` for no dev set or an empty one.

### 5.8 The ablation: layout, config, plan, preparation, records, loop, report

- `ablation_layout.variant_paths(out_dir, variant_id) -> VariantPaths` and `data_dir(out_dir)`: `data/`, `variants/<id>/{config.yaml, valid.src, valid.tgt, run/{vocab.src, ckpt/}, eval/, train.json, result.json}`; no disk access.
- `ablation_config.variant_overrides(matrix, variant, *, spm_model, paths, corpora, weights)` and `variant_config(...)`: the per-run values (`seed`, `src_vocab`, `data`, `transforms_configs.sentencepiece` for both sides, `training.model_path`; every path absolute POSIX) with the matrix overrides layered over them (a `None` kept, so it deletes the base's key), merged over the base and validated. The corpora run `filtertoolong` when the base plus the overrides configure `transforms_configs.filtertoolong`.
- `plan_ablation(matrix, corpus_paths, spm_model, out_dir) -> AblationPlan` (in `ablation_plan`): reads the training and the dev rows from the same corpus files (R2, R7; the dev loader gets the training rows, so `dev_in_train` is counted), and returns the statistics, the dev statistics, the variants, and per variant the corpus sizes, probabilities, integer weights (summing to `weight_total`) and upsampling (R5), the bt usage and the collision rate; no training, no file and no directory is written (the dry run prints it). Matrix `overrides` may not touch `RESERVED_OVERRIDE_KEYS` (`data`, `src_vocab`, `seed`, `training.model_path`, `transforms_configs.sentencepiece`, also by replacing or deleting a parent section): a `ConfigError` naming the key, at plan time. A `ValueError` of the sampling is a `ConfigError` naming the variant; more corpora than `weight_total` is the `ConfigError` of `integer_weights`; a `$` in `out_dir` or the SentencePiece path is a `ConfigError`, and so is any of `[`, `]`, `*`, `?` in `out_dir` as an absolute path (finding 10); the plan also checks, for every variant and without writing, the Eole config its preparation would render (through `variant_config` and `validate_train_config`) and that the SentencePiece model loads and has every direction tag as one piece, each a `ConfigError`; a mixture without any corpus is a `DataError`.
- `prepare_variant(plan, planned, *, threads) -> PreparedVariant`: builds the variant's corpora, writes its validation corpus into `variants/<id>/`, renders `variants/<id>/config.yaml` (`render`) and returns the paths, the corpora, the config text and the fingerprint inputs: the SHA-256 of the config text, of both files of every corpus and of the validation files, of the raw dev source and reference texts by direction, of the SentencePiece model, the thread count, the installed versions of Eole, torch, SentencePiece and sacrebleu (`not installed` for a missing one) and the tag placement; the fingerprint is the SHA-256 of their canonical JSON. The config text holds absolute paths, so moving the output directory or the model retrains; the checkpoint hashed by the manifest is the artefact of record. `ValueError` below one thread.
- `run_ablation(plan, *, threads, timeout, force, train=run_training, evaluate=evaluate_variant, progress=None, clock=time.perf_counter) -> AblationResult`: per variant in order: prepare; a variant is COMPLETE per R10 and then reused (neither seam is called), unless `force`. Otherwise the stale `result.json` is removed; a variant whose `train.json` vouches for the current fingerprint and its checkpoint (not with `force`) skips `train`, any other has its stale `train.json` removed, `train(config, run_dir, validate=validate_train_config, threads=, timeout=)` runs (a training that leaves no checkpoint file is an `UpstreamError`) and `train.json` is written (atomically) as soon as the checkpoint is hashed; then `evaluate(ckpt_dir, dev, spm_model=, placement=, out_dir=variants/<id>/eval, threads=, timeout=)` runs (an evaluation that scored other dev sets than the plan's is an `UpstreamError`) and `result.json` is written LAST (atomically), so a crash leaves the variant incomplete and, once it has trained, resumable at the evaluation. A failure of a seam, and a keyboard interrupt, stops the run unchanged, leaving earlier variants complete. `progress` gets a frozen `VariantProgress(variant_id, index, total, outcome, train_seconds, eval_seconds)` after each variant (`outcome` is `trained`, `evaluated` or `reused`; the seconds are those of this call: no training seconds unless it trained, none at all if it reused); `clock` times the seams. `AblationResult(plan, threads, variants)` holds one `VariantResult` per variant, with the SHA-256 of its checkpoint file, for the manifest.
- Outputs under `out_dir`: as in `ablation_layout`, and, written by `run_ablation` also when every variant was reused, `results.tsv` (a header and one row per variant: `variant`, `temperature`, `bt_ratio`, `tag_placement`, `seed`, then `chrf_<d>` and `bleu_<d>` interleaved for each direction `d` in sorted order, then `chrf_mean`, `chrf_min`, `tag_leaks`, `train_seconds`, `source_collision_rate`; scores to two decimals, the source collision rate to four, seconds to one, the axes as in the id), `results.json` (everything: the matrix, both statistics, and per variant its axes, fingerprint, corpora with probabilities, weights and upsampling, bt usage, the raw `DevResult`, seconds, checkpoint file and hash, status), `results.md` (the main columns and a summary over the seeds by `(temperature, bt_ratio, tag_placement)`, averaging `chrf_mean` and `chrf_min` with the number of seeds). The tables are written when every variant is done, not before.
- `source_collision_rate` in the table is that of the kept training rows before any bt subsample (one number for the run, repeated on every row).

### 5.9 CLI `rinchen train ablate`

`--matrix PATH` (required), `--corpus PATH` (required, repeatable; the same file twice is refused), `--spm-model PATH`, `--out-dir PATH`, `--threads INT` (default 2, at least 1), `--timeout FLOAT` (seconds per Eole command; positive and finite), `--force`, `--dry-run`. Exit codes as D4 to D6 (`rinchen_errors_as_exit_codes`: `ConfigError` 2, `DataError` 3, `UpstreamError` 4, other 1; interrupt 130; SIGTERM 143 and SIGHUP 129, which `run_logged` turns into `SystemExit` so that Eole's process group is killed too; SIGKILL cannot be caught, and an `eole` left running after `kill -9` of `rinchen` is a known limit). Order of work: refuse a bad `--timeout` and a repeated `--corpus`; on a real run hash the matrix; load the matrix; refuse a foreign manifest in `out_dir` (D4's `refuse_foreign_manifest`) and an `out_dir` that is an input's directory (both also on a dry run); hash the base config, the corpora and the SentencePiece model (each input is hashed before it is read); plan; on `--dry-run` print the plan and stop (it creates nothing); create `out_dir` before paid work; remove the old manifest (`begin_commit`); `run_ablation`; write the manifest last. The dry run prints one fact per line (matrix, out dir, weight total, corpus files, the mixture statistics, the dev statistics, the variants, per variant the bt usage and each corpus with rows, probability, weight and upsampling) and ends with `nothing was trained and nothing was written`. A real run prints one line per variant, `variant <i>/<n> <id> <outcome> train <s> s eval <s> s`, then `variants: <n> (trained <a>, evaluated <b>, reused <c>)`, `manifest: <path>` and the three result tables (standard output; errors on standard error). The manifest (stage `train_ablate`) lists the matrix, the base config, the corpora and the SentencePiece model as inputs, and the three tables, each variant's rendered config and its checkpoint (with the digest the variant recorded) as outputs; `config_sha256` is the matrix hash, `seed` the first seed, `metrics` the flattened statistics, `variants.*`, `threads` and `seed.<n>`, `tool_versions` eole, torch, sentencepiece, sacrebleu and polars, `status` `{"ablation": "ok"}`. An `OSError` creating or writing the outputs is exit 1.

## 7. Open questions, recorded as such

- The proxy config for real ablations (`configs/eole/multilingual_proxy.yaml`, `ablation_priors.yaml`) is a set of unmeasured priors, validated by schema tests only (Eole's `TrainConfig` accepts them); no GPU run exists.
- Whether the weight resolution of 100 is enough for 16 directions with a bt corpus each (32 corpora): computed in the runbook (at T=1 half the corpora sit at weight 1 and the smallest is drawn 5.5 times its proportion; 200 halves that error at T=0.5 and 1.0), never trained; the guard fails loudly only below one weight per corpus.
- Writing the training text files for hundreds of millions of rows: the training loader holds the kept rows of all directions in one frame. Measured at 1,000,000 and 4,000,000 synthetic rows (0.32 s and 1.09 s to load; 1.55 GiB and 4.76 GiB peak); extrapolated, 46 GiB would be reached near 44M rows. A streaming loader would be needed beyond that.
- `xavier_uniform` initialisation converged much faster on the toy; it is NOT adopted (an unmeasured effect at scale); `param_init_method` is an allowed key so an ablation can try it.
- CTranslate2 export and Eole-native prediction of a tag-on-target model; `num_workers` above 1 with weights; GPU determinism; the evaluation runs on the CPU even for a GPU-trained proxy model.
