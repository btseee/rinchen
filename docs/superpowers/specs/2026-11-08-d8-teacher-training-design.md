# D8 Teacher training: design

Status: binding for the D8 plan (`docs/superpowers/plans/2026-11-08-d8-teacher-training.md`). Written before the build and amended to the finished code in Task 8 (2026-11-08): sections 3 to 7 describe what was built, and section 8 lists each ruling and decision made while building. The operator's view, with real output, is `docs/runbooks/08_teacher.md`. Master plan: `docs/research/2026-10-29-rinchen-dev-agent-prompt.md`, milestone D8. Evidence for every Eole fact: `.superpowers/sdd/2026-11-08-d8-teacher-training/spike-findings.md` (a spike on this machine, Eole 0.6.4, CPU, toy data; scratch scripts named there).

## 1. Goal and non-goals

Goal: a resumable, operator-friendly launcher for long Eole trainings. `rinchen train launch` takes a rendered, validated Eole config and a run directory, builds the vocabulary if needed, trains, resumes from the latest COMPLETE checkpoint of the same run after any interruption, recognises completion and early stopping, writes a `command.sh` an operator can run by hand (for example the 8-GPU command), and records what it did; `rinchen train average` averages the last N checkpoints into a usable model. STOP gate: a tiny teacher checkpoint is trained for 200 CPU steps without NaN with the training loss falling by at least 30 %, is interrupted-and-resumed correctly, saved and averaged (met on the CPU with the real binary: the loss fell 60.7 %).

Non-goals:
- No GPU was used and none is claimed: this machine has an RTX 5070 Ti that the owner did not authorise for a run, so every GPU, NCCL, bf16/fp16, flash-attention and multi-GPU statement is read from Eole's source or from a CPU gloo shim and is labelled UNMEASURED. `configs/eole/teacher.yaml` holds unmeasured priors from the master plan.
- No real data exists: the tiny teacher trains on the D7 toy set; its quality numbers rank nothing.
- No document-level data (D9), no distillation (D10), no CTranslate2 export (D11), no evaluation suites (D12, D13).
- No fine-tuning: a resume continues OUR OWN interrupted run from OUR OWN checkpoint inside the same run directory; `train_from` is never accepted for a foreign path.

## 2. Findings that bind the design (spike)

1. Resume is `training.train_from: <model_path>/step_N` (a directory with `config.json`, `vocab.json`, `optimizer.pt`, the weights); `train_steps` is the ABSOLUTE target; weights, Adam state, step counter and the noam schedule are restored; the optimizer OPTIONS come from the checkpoint's saved config (a new learning rate in the resume YAML is silently ignored); the DATA STREAM RESTARTS from the first line of every corpus; scheduled `accum_count`/`dropout` lists restart at their first value. A resumed run differs from an uninterrupted one (58 of 62 tensors, valid ppl 8.61 vs 8.82 on the toy) but a resume is deterministic.
2. Eole's checkpoint saver is not atomic: the root `model_path/*` entries are relative symlinks into `step_N/` updated one by one, so a kill mid-save can leave a silent mix (weights from step 50, optimizer from step 100). Resume must name a COMPLETE `step_N` directory, never `model_path` itself. Completeness: all four files exist; `config.json` and `vocab.json` parse; `safetensors.safe_open` opens the weights; `zipfile.ZipFile` opens `optimizer.pt`. `config.json` is written last. Every truncation tried is caught.
3. Resuming a FINISHED run trains one extra step (step_61 after train_steps 60): a finished run must not be resumed. A fresh launch into a `model_path` that already holds step directories is not refused by Eole: provenance must be recorded.
4. Eole has NO averaging tool. `average_decay`/`average_every` is an exponential moving average whose EMA REPLACES the live weights in every saved checkpoint (the live weights are never saved) and is not restored on resume: not allowed in configs. We average saved checkpoints ourselves (float64 mean of the safetensors tensors, rounded to each tensor's dtype); the output works in `eole predict`. On the toy, averaging neither helps nor hurts beyond noise (and hurts in the steep part of the curve): the runbook says so.
5. Eole prints, every `report_every` steps, `Step  10/  200; acc: ...; ppl: ...; xent: ...` and, at each validation, `Validation perplexity: ...` and `Validation accuracy: ...` (no xent line, no step number); ppl/xent include label smoothing. A NaN loss prints `nan` and training CONTINUES to the end with exit code 0 and NaN checkpoints: a harness must grep for nan/inf.
6. `eole train` spawns the per-GPU processes itself (`world_size` > 1 spawns one process per entry of `gpu_ranks`); there is no torchrun and no `RANK`/`WORLD_SIZE` environment. Rules: `world_size` >= `len(gpu_ranks)`; when equal and positive, `min(gpu_ranks)` must be 0; `world_size` 2 with `gpu_ranks` [] is a SILENT no-op (exit 0, no checkpoint). `training.timeout` (60 s by default) is the collective timeout: rank 0 alone validates and saves, the others wait, so a slow validation or a multi-GB save beyond `timeout` kills the job.
7. Early stopping runs on rank 0 only; the final checkpoint is written complete and then a multi-process job dies after `timeout` seconds with exit code 1 (a single-process job exits 0). Eole keeps the LAST `keep_checkpoint` checkpoints, never the best one. A Ctrl-C makes Eole exit 0 without a final checkpoint.
8. With several corpora, `all_gather_stats` pickles per-corpus statistics into a 4096-byte buffer: the pickle is 4.0 KB at 100 corpora (the crash is source-derived, untested).
9. Same seed AND same thread count give byte-identical checkpoints. Unknown config keys are rejected by `eole train`.

## 3. Rulings

S1. `launch` is a separate runner from D7's `run_training`: `run_training` treats any fresh `model.00.safetensors` as success and cannot resume; D7's short ablation runs keep it. Both use `run_logged` and the shared environment helpers; `run_logged` gained `inherit_fds` for S2's lock.
S2. Run identity. `launch.json` in the run directory (`schema_version` 1, `identity`, `world_size`, `gpu_ranks`, `created`) records the sha256 of the canonical JSON (sorted keys, no spaces, non-ASCII as it is) of the EFFECTIVE config (after the `--world-size`/`--gpu-ranks` overrides, both spelled out) with `training.train_steps` and `training.train_from` removed (`checkpoints.IDENTITY_EXCLUDED_KEYS`). The identity is enforced when the checkpoint directory holds step directories: with none, the record is written or rewritten and the launch is a fresh start; with step directories and a different identity, or without a `launch.json`, the launch is a `ConfigError` naming the problem (resume would silently ignore changed optimizer options). Extending `train_steps` is the one allowed change; lowering it below the newest complete step is a `ConfigError`. A different GPU count is a different identity (the effective batch changes). Paths are in the config and so in the identity.
A real `launch` holds an exclusive non-blocking `flock` on `run_dir/launch/lock` from before it reads the run until it returns; a second launch into the run is a `ConfigError` naming the lock file, and `--write-only` is refused while the lock is held (it only looks, takes no lock, and creates no file). The lock dies with the process, so a crash leaves nothing stale. The descriptor is handed to `eole build_vocab` and `eole train` (`run_logged(inherit_fds=)`), so when the launcher is killed with SIGKILL the Eole it started, which outlives it, keeps the lock until it exits and a second launch cannot start another training into the same checkpoint directory. The holder is Eole's leader: the per-rank processes of a multi-GPU run are spawned with `close_fds` and do not hold the descriptor, so the lock lasts as long as the leader. `run_logged` therefore also kills the whole process group when the leader exits non-zero on its own (a clean exit 0 is not followed by a kill), so a crash of the leader with the launcher alive leaves no rank training; after a SIGKILL of the launcher nothing sweeps the group. The lock is advisory and local: a hand-run `command.sh` neither takes nor sees it, and `flock` on NFS or Lustre was not checked.

S3. Resume rule. The candidates are the `step_N` directories of `model_path`; the newest COMPLETE one is the resume point (incomplete newer ones are reported and ignored; Eole overwrites them). `train_from` is allowed ONLY in a config that `launch` itself renders for an attempt that resumes, and only as `<training.model_path>/step_N` with N positive and no leading zero, no `..` and no glob character (`validate_train_config(..., resumes=True)`, which accepts a config that leaves `train_from` out; everywhere else it stays an unknown key; the launcher passes the complete directory it found). Every attempt k has its own effective config `run_dir/launch/train-<k>.yaml` (the config file with the overrides laid over it and, when it resumes, `training.train_from`) and its own log `run_dir/launch/attempt-<k>.log`; k is the highest existing log number plus one. The config file the operator gives is never edited, and `command.sh` and the record name exactly what ran.
S4. Outcomes of `launch` (`LaunchResult.status`): `already_complete` (a complete `step_<train_steps>` exists, or the last attempt early-stopped at the newest complete step: nothing is run), `completed` (the run reached `train_steps`), `early_stopped` (the log has `Early Stop!` and the step saved right after it is the newest complete step, whatever the exit code), `written` (`--write-only`), each with `resumed_from` (a step or None). `train_steps` must be an explicit positive integer in the config (Eole's default of 100000 would otherwise apply without a word). Failures: `UpstreamError` for a non-zero exit without an early stop, for exit 0 without the final step and without an early stop (an interrupted run), and for a NaN or infinite figure anywhere in the log (the run is finished but the checkpoint is bad: the message names the first step and the field); `ConfigError` for identity mismatches, `train_steps` below the newest complete step, the lock and the GPU rules; `DataError` for an invalid `launch.json` or an unlistable checkpoint directory. The NaN gate runs when an attempt ENDS (there is no live abort), and a later launch refuses a run whose last attempt logged a non-finite figure at or before the newest complete step instead of resuming it or calling it finished. An early stop that lands exactly on `train_steps` is reported `early_stopped` by the launch that ran it and `already_complete` by the next one.
S5. GPU rules enforced by `launch` before anything starts: `world_size` and `gpu_ranks` rules of finding 6, including refusing `world_size` > 1 with empty `gpu_ranks`; `training.timeout` at least 3600 when `world_size` > 1; at most 80 training corpora when `world_size` > 1; `training.early_stopping_criteria` a single string when early stopping is on; `keep_checkpoint` at least `early_stopping` + 1 when early stopping is on and `valid_steps` equals `save_checkpoint_steps` (else the best checkpoint may be deleted). `--cuda-visible-devices` is digits separated by commas, names at least one device per rank and is refused for a run without a GPU, which always hides every device from Eole.
S6. `command.sh` is deterministic text (golden-tested with an injected `eole` path; every path in it absolute): `#!/usr/bin/env bash`, comments that state the run directory, the attempt and whether it starts from scratch or resumes from step N (fixed at write time; regenerate with `--write-only`), `set -euo pipefail`, the thread variables, `CUDA_VISIBLE_DEVICES` only when requested (or empty for a run without a GPU), a `cd` to the working directory of the launch, `mkdir -p` of the log directory, a guarded `eole build_vocab -config <train-k.yaml> -n_sample -1 2>&1 | tee -a launch/build_vocab.log` (`[ -f vocab ] || ...`) and `eole train -config <train-k.yaml> 2>&1 | tee -a launch/attempt-<k>.log`. The `tee -a` (with `pipefail`, so the status stays Eole's) makes a hand-run attempt leave the log that a later `launch` reads for a NaN or an early stop; without it a run started by hand was invisible to the launcher. `--write-only` writes `command.sh`, `launch/train-<k>.yaml` and `launch.json` (so a run an operator started by hand from the script can be resumed by `launch` afterwards: a record without step directories is a fresh start; the same refusals hold as for a real launch) and nothing else; it leaves an existing manifest, whose `command.sh` digest is then stale.
S7. Averaging. `average_checkpoints(step_dirs, out_dir)`: at least two COMPLETE step directories of one checkpoint directory (same tensor names, shapes and dtypes, else `DataError`; NaN or infinity refused), a plain mean per floating tensor summed in float64 and rounded to nearest-even in the tensor's dtype (bfloat16 through its bit pattern, float64 to float32 to bfloat16), non-float tensors and tensors bit-for-bit equal in every source (the position buffers, `layer_scalar`) taken from the last directory, `config.json`/`vocab.json`/the SPM artifact copied from the last, no `optimizer.pt`; the safetensors file is written by its format (streaming, deterministic bytes) and checked with `safetensors`; the directory is built under a temporary name and renamed, so it appears whole or not at all; `averaged_from.json` records the sources and the sha256 of every input weights file and of the output. The output is not a checkpoint (no optimizer state, never named `step_N`). Peak memory is about 9 times the largest float tensor. `average_decay` stays out of the allow-lists.
S8. Loss gate. `parse_train_log(text)` extracts the training curve of the LAST run in a log and its validation perplexities; `loss_gate(curve, min_drop=0.3)` returns None or a reason (it returns a reason rather than raising, and raises `DataError` only for a log with fewer than two reports or two validations). The tiny teacher gate is: no NaN/inf anywhere, `xent` at the last report at most 0.7 times the `xent` of the first report (a fall of at least 30 %; the spike measured 60.4 to 62.4 %, the gate run 60.7 %), and the last validation perplexity below the first. `launch` itself applies only the NaN rule; the loss gate is applied by the integration test, to the log of the first attempt (the log of a resumed attempt starts at the resume and falls less).
S9. Configs. `configs/eole/teacher.yaml` is the 8-GPU prior from the master plan (hidden 1536, encoder 24 / decoder 12, 16 heads, ff 4096, bf16, 16384-token batches x accum 8, dropout 0.1, valid/save every 5000, early stopping 6 on `ppl`, label smoothing 0.1, `timeout` hours, `tensorboard` on, `batch_size_multiple` 8); every value is labelled an unmeasured prior; it passes the schema validator and Eole's own schema in a test, nothing more. `configs/eole/teacher_tiny.yaml` is the CPU gate config (the D7 tiny base shape with 200 steps, `report_every` 10, `valid_steps` = `save_checkpoint_steps` 50, `keep_checkpoint` 4). The data section and the per-run paths come from D7's `prepare_variant` (`rinchen train ablate --prepare-only`), so a teacher run uses the mixture settings chosen by the ablations. `teacher.yaml` sets `tensorboard: true` without `tensorboard_log_dir`, whose Eole default is the relative `runs/eole` (events outside the run directory); `launch` therefore puts `tensorboard_log_dir: <run directory>/tensorboard` (absolute) into the effective config when `tensorboard` is true and the config names none (final review, I-2): it is in every rendered attempt config and in the identity, like any effective value, and a directory the config names is kept. The comment of `teacher.yaml` cites master plan lines 511 to 514 where the teacher block is 511 to 516 (configs were not touched; still open).
S10. The validation corpus stays D7's pre-tokenised one; `valid_metrics` is not used in teacher configs (it would score piece strings); BLEU/chrF of a teacher comes from `evaluate_variant` after training.

## 5. Contracts (as built)

- `eole_cfg`: new TRAINING keys `early_stopping`, `early_stopping_criteria`, `timeout`, `master_ip`, `master_port`, `gpu_backend`, `normalization` (`NORMALIZATIONS` = `sents`, `tokens`), `batch_size_multiple`, `self_attn_backend` (the training section has 36 keys); new TOP_LEVEL keys `tensorboard`, `tensorboard_log_dir`, `log_file` and `valid_metrics` (allowed, no teacher config sets it; the top level has 19). `train_from` is in `RESUME_TRAINING_KEYS`, not in `TRAINING_KEYS`: `validate_train_config(cfg, *, resumes=False)` allows it only with `resumes=True`, where it must be `<training.model_path>/step_<N>` (`merged_config` and `render` take `resumes` too). Value rules: booleans, non-empty strings, non-negative or positive integers, a port from 1 to 65535, `normalization` one of two; a bool is not an int. Not added: `average_decay`, `average_every`, `accum_steps`, `dropout_steps`, `reset_optim`, `update_vocab`. Drift tests cover every added key against the installed Eole.
- `checkpoints`: `StepDirectory(step, path, problem, of_another_model=False)` with a `complete` property (`problem is None`); `ResumePoint(directory, incomplete_newer)` (the newer directories that cannot be resumed from: incomplete, or complete and of another model); `step_directories(model_path) -> list[StepDirectory]` sorted by step (a real directory named `step_<N>`, N positive without a leading zero; links and other names are left out; an absent `model_path` is empty; a file there is a `DataError`); `latest_complete(model_path, *, model=None) -> ResumePoint` (with the config's `model` section, a complete directory whose saved `config.json` describes another model is passed over like an incomplete one, `of_another_model` set); `architecture_mismatch(saved_config, model) -> ArchitectureMismatch | None` (the first key of `architecture`, `hidden_size`, `heads`, `transformer_ff`, the embeddings' width and position scheme and the stacks' layers, width, heads, feed-forward size and position scheme that both sides set to different values; a key either side lacks is not compared; best effort, not proof of provenance); `step_of(path) -> int | None`; `is_complete(step_dir) -> str | None` (None = complete, else the first problem, starting with the file name; a file that cannot be read is `<name>: cannot be read (<exception class>: <reason>)`; it checks `config.json`, `vocab.json`, `optimizer.pt`, `model.00.safetensors` in that order and NEVER raises for a damaged directory); `identity_of(cfg) -> str`; `RunIdentity(identity, world_size, gpu_ranks, created)` (strict pydantic model); `write_launch_record(run_dir, record)` (atomic) and `read_launch_record(run_dir) -> RunIdentity | None` (strict; `DataError` for anything `write_launch_record` could not have written, or over 64 KiB). Constants `WEIGHTS_FILE`, `OPTIMIZER_FILE`, `CONFIG_FILE`, `VOCAB_FILE`, `LAUNCH_FILE`, `IDENTITY_EXCLUDED_KEYS`.
- `curves`: `parse_train_log(text) -> TrainCurve(reports, validations, accuracies, saved_steps, early_stopped, early_stop_step, non_finite_step, non_finite_field, runs, unparsed_reports)` with `reports` a tuple of `TrainReport(step, total, acc, ppl, xent, lr)`; the curve is the LAST run when the steps go backwards (`runs`, `restarted`), `non_finite_*` covers the whole log; `loss_gate(curve, min_drop=0.3) -> str | None`.
- `average`: `average_checkpoints(step_dirs: Sequence[Path], out_dir: Path) -> AveragedModel(directory, weights_sha256, sources, tensor_count, averaged_count, copied_files, skipped_entries)`; `AVERAGED_FROM_FILE` = `averaged_from.json`. S7.
- `gpu_rules`: `check_gpu_rules(cfg) -> GpuSettings(world_size, gpu_ranks)` (property `uses_gpu`); `ConfigError` messages are `invalid Eole config: <dotted.path>: <problem>`; constants `MIN_MULTI_PROCESS_TIMEOUT_S` = 3600, `MAX_TRAINING_CORPORA` = 80.
- `launch_command`: `render_command_sh(*, run_dir, working_directory, eole, config, src_vocab, attempt_log, build_vocab_log, threads, cuda_visible_devices, attempt, resumes_from) -> str`; every path must be absolute (`ValueError`); S6.
- `run_lock`: `holding_the_run(lock: Path)`, a context manager that yields the descriptor number for `inherit_fds`; `refuse_a_held_run(lock: Path)`.
- `launch`: `launch(cfg_path, run_dir, *, world_size=None, gpu_ranks=None, threads=2, timeout=None, write_only=False, eole=None, cuda_visible_devices=None, extra_env=None, before_writing=None) -> LaunchResult(status, steps, resumed_from, checkpoint, command_sh, log, attempt, incomplete_skipped)`. `status` is `completed`, `early_stopped`, `already_complete` or `written`; `steps` is the newest complete step when the launch ended (for `written`, the one it would resume from); `checkpoint` is the directory of `steps` (None for `written`); `command_sh` is None when nothing was written; `log` is the attempt's log (None when no Eole ran); `attempt` is 0 when no attempt was prepared; `incomplete_skipped` the steps of the incomplete directories above the resume point. `before_writing` is called once, right before the first file of an attempt is written and after every refusal and the finished-run check (so not for a refused launch or a run found finished); what it raises propagates with nothing written. `extra_env` is a hook for a test shim, never read from the environment. `latest_attempt_log(run_dir) -> (number, path) | None`.
- CLI: `rinchen train launch --config --run-dir [--world-size --gpu-ranks --threads --timeout --write-only --cuda-visible-devices]` prints `status`, `steps`, `resumed from`, `attempt`, `checkpoint`, `log`, `command.sh`, optionally `incomplete step directories skipped`, then `manifest` (each `key: value`, `none` for an absent value); with `--write-only` it prints the path of `command.sh` and nothing else (for a finished run a note on standard error and no path, exit 0). `rinchen train average --checkpoint-dir D --last N [--out]` (D is the run's `training.model_path`, not the run directory: its name is the config's choice, and the default output is `averaged` beside it) prints `averaged: N checkpoints (steps a, b, ...)`, `output`, `weights sha256`, optionally `incomplete step directories skipped`, `manifest`. `rinchen train ablate ... --prepare-only` prints `prepared <id>: <config.yaml>` per variant and `manifest: ...` (stage `train_prepare`, kept apart from `train_ablate` because it vouches for configs and data, not for results; `--force` and `--timeout` are refused with it, `--threads` is only recorded, `--dry-run` wins; each stage refuses the other's manifest, so prepare-then-ablate into one out dir is refused both ways). Exit codes as D4 to D7. Manifests as D7 (inputs hashed before they are read, manifest last): `train_launch` (inputs: the config; outputs: the four files of the final step directory, never the links Eole puts in the checkpoint directory, plus `launch.json` and `command.sh`; metrics `steps`, `attempt`, `incomplete_skipped`, `early_stopped`, `resumed_from` when the attempt resumed, and from the last attempt's log `xent_first`, `xent_last`, `valid_ppl_first`, `valid_ppl_last`; `tool_versions` eole, torch, safetensors, sentencepiece; `seed` the config's or -1) and `train_average` (inside the output directory, the last file written: inputs the weights files of the averaged steps; outputs the averaged weights, `averaged_from.json` and the copied files; metrics `checkpoints`, `first_step`, `last_step`, `tensors`, `tensors_averaged`; `tool_versions` safetensors and numpy). The manifest of `launch` is dropped by the `before_writing` hook, so a refused launch, a launch turned away by the lock or a run found finished leaves it alone (a finished run's manifest is rewritten only when missing or no longer vouching for the same files), and a launch that fails after it started leaves none. The code is `cli/train.py` (`ablate`), `cli/train_runs.py` (`launch`, `average`) and `cli/train_common.py` (the checks they share).

## 6. Tests and the gate

- Unit tests with fakes for everything but Eole (fabricated step directories with real small safetensors and zip files; truncation matrices; `run_logged` faked by `FakeEole`; `command.sh` run by bash against an executable stand-in), property tests for the checkpoints, curves and averaging, and a drift test for the added allow-list keys against the installed Eole.
- STOP gate (`tests/integration/test_train_tiny_teacher.py`, 30 tests collected from 27 functions (28 from 25 before the final review's fixes, which added scenario I, the `eole train` leader killed on its own), marker `subprocess`: the real `rinchen` binary and the real `eole` on the CPU). Scenarios: A prepare the one-variant tiny teacher with `rinchen train ablate --prepare-only`, launch it for 200 steps (about 30 s): exit 0, `completed`, no NaN, xent(200) <= 0.7 x xent(10), last validation perplexity below the first, `launch.json` written; B a second launch is `already_complete` and touches nothing; C truncating the weights of `step_200` and launching again resumes from `step_150` (the log starts at `Step 160/  200`) and completes; D a separate run of 100 steps extended to 200 resumes from `step_100` (`Step 110/  200`), and lowering `train_steps` is refused; E a changed learning rate is refused and Eole is not started; F `rinchen train average --last 3` writes a model that `evaluate_variant` translates with (plumbing only, no quality threshold); G a real SIGTERM mid-run and before the first checkpoint ends the launcher with 143, leaves no descendant of Eole, frees the lock, and the next launch finishes the run; H a launch or `--write-only` into a run that another launch holds is refused naming the lock. Task 7, the optional two-rank CPU gloo run through a test-only shim, was NOT written (section 8).
- The gate: `uv run ruff format --check . && uv run ruff check . && uv run mypy src && uv run pytest -m "not network" -q` (7114 passed, 1 skipped, 10 deselected at the last record, never `-W error`).

## 7. Open questions, recorded as such

- Every GPU-side behaviour (NCCL, bf16, flash attention, the 13 GB checkpoint write, the double division by `world_size`, multi-node) is unmeasured; the teacher prior values are unmeasured. No GPU was used: this machine has an RTX 5070 Ti that the owner did not authorise for a run; a one-GPU smoke test awaits that authorisation.
- The data position is not restored on resume (the corpora replay from the first line): the bias this introduces for a long run with few resumes is unmeasured.
- Whether checkpoint averaging helps a real teacher is unmeasured; the toy cannot show it.
- The NaN gate runs when an attempt ends; a live abort is not built.
- `flock` on network file systems is unchecked; the lock does not guard a hand-run `command.sh`.
- `--write-only` leaves an existing manifest with a stale `command.sh` digest; an `already_complete` rerun re-hashes the final step directory (GB scale for a real teacher); curve metrics in the manifest come from the last attempt's log only; the manifest is written just after the lock is released; the identity-mismatch message cannot say which key differs; there is no CLI way to force a CPU run of a GPU config.
- D9 (continued training of OUR teacher) will need a conscious extension of the identity rule: `train_from` is allowed only as the launcher's own resume.
